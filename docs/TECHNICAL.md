# Техническая документация

Документ описывает состав системы, устройство ядра, применяемые движки и модели, настройки, данные, повторение замеров качества, тестирование и условия эксплуатации. Установка, запуск и работа с веб-интерфейсом изложены в [README](../README.md). Архитектура и основания решений приведены в [ARCHITECTURE.md](ARCHITECTURE.md) и [docs/adr](adr), формат отчёта в [report-format.md](report-format.md) и [report.schema.json](report.schema.json), результаты на 11.11.2026 в [промежуточном отчёте](reports/2026-11-11-interim.md).

## 1. Состав системы

Система состоит из ядра, которое выполняет всю обработку, и оболочек над ним. В API и веб-интерфейсе нет логики проверки. Они принимают комплект, запускают ядро и показывают его отчёт.

*Таблица 1. Компоненты*

| Компонент | Каталог | Назначение | Технологии |
| --- | --- | --- | --- |
| Ядро `kdcheck` | `packages/kdcheck` | Конвейер обработки, правила Блоков 1 и 2, контракт отчёта, выгрузки, командная строка `kdcheck run` | Python 3.11 и новее, pydantic, pypdfium2, Pillow, PyYAML, openpyxl. Для растров и сканов onnxruntime с numpy и Tesseract через pytesseract |
| API | `backend/arm_web` | Приём комплекта, задания, запуск ядра отдельным процессом с лимитами, выдача отчёта, выгрузок и изображений листов | FastAPI, uvicorn |
| Веб-интерфейс | `frontend` | Отчёт по комплекту, просмотр листа с подсветкой источника значения | React, TypeScript, Vite. Типы отчёта генерируются из JSON Schema |
| Генератор синтетики | `synth` | Комплекты по ГОСТ с разметкой и заложенными ошибками, растры и сканы заданного качества | reportlab, pypdfium2, Pillow. Augraphy нужен только для сборки замороженного стрессового корпуса |
| Оценка качества | `eval` | Замеры, эталонная разметка, результаты в `eval/results` | Python |
| Настройки | `configs` | Пороги, шаблоны форм ГОСТ, словари, правила, движки, лимиты | YAML с проверкой моделями pydantic |
| Промпты | `prompts` | Тексты запросов к мультимодальной модели с версиями | Текстовые файлы |

Ядро не зависит от API, генератора и оценки, а Блоки 1 и 2 не импортируют друг друга. Эти границы при каждом изменении проверяет import-linter ([ADR-0011](adr/0011-core-public-api.md)).

Ошибка разбора одного файла записывается в журнал отчёта и не прерывает обработку остальных файлов. Сбой на одной странице отмечается только у этой страницы.

## 3. Движки и модели

Все движки работают на той же машине, что и ядро. Выбор движка и его параметры задаются в `configs/models.yaml`. Отчёт записывает имя и версию каждого движка, а у каждого значения указан движок, которым оно получено.

*Таблица 3. Движки*

| Задача | Движок | Лицензия | Когда применяется |
| --- | --- | --- | --- |
| Текстовый слой и изображения PDF | pypdfium2 (PDFium) | Apache-2.0 или BSD-3-Clause, у PDFium BSD-3-Clause | Всегда. PyMuPDF с лицензией AGPL-3.0 подключается только для отката и в поставку не входит ([ADR-0007](adr/0007-pdf-library.md)) |
| Ячейки основной надписи и строк спецификаций растров и сканов | PP-OCRv5 для восточнославянских языков через onnxruntime | Apache-2.0, у onnxruntime MIT | Если файлы модели загружены скриптом `scripts/fetch_ppocr.sh` из закреплённой ревизии ([ADR-0024](adr/0024-ppocr-cells.md)) |
| Текст листа растра и скана, резерв для ячеек | Tesseract 5 с языком `rus` | Apache-2.0 | Когда нет файлов PP-OCRv5, а также для текста листа вне ячеек |
| Ячейки основной надписи и строк спецификаций, блок технических требований растров и сканов | Мультимодальная модель на OpenAI-совместимом сервере, по замеру выбрана Qwen3.6-35B-A3B | Apache-2.0 | По флагу `--vlm`, по умолчанию выключена ([ADR-0014](adr/0014-local-vlm.md), [ADR-0019](adr/0019-vlm-main-reader.md), [ADR-0021](adr/0021-vlm-spec-rows.md), [ADR-0023](adr/0023-vlm-tech-requirements.md)) |

Мультимодальная модель только читает текст вырезанной ячейки или блока. Значение нормализуют те же правила, что и для OCR, а областью-источником остаётся ячейка бланка. Если прочтение модели расходится с OCR, в отчёт идёт прочтение модели со статусом `conflict`, а прочтение OCR сохраняется в заметках документа. Адрес сервера модели за пределами этой машины отклоняется проверкой настроек, пока в них явно не разрешена удалённая обработка. Такое разрешение может дать только заказчик.

## 4. Настройки

Пороги, шаблоны форм, словари, правила, движки и лимиты хранятся в `configs/*.yaml` ([ADR-0012](adr/0012-configs.md)), назначение каждого файла перечислено в [README](../README.md#настройки). При запуске настройки проверяются моделями pydantic, и неизвестный ключ или неверное значение останавливают обработку с указанием файла и поля. В отчёт записывается SHA-256 действующих настроек, поэтому по отчёту видно, с какими порогами он получен. Собственный набор настроек делается копией каталога с правками и передаётся ключом `--config` или переменной `ARM_CONFIG_DIR`.

## 5. Контракт отчёта

Отчёт описан моделью `Report` из `kdcheck.schemas`, версия контракта 1.9. Из моделей генерируются JSON Schema ([report.schema.json](report.schema.json)) и типы TypeScript веб-интерфейса (`scripts/export_schema.sh`), а тесты сверяют схему и типы с моделями. Новые поля добавляются необязательными, поэтому отчёты прежних версий остаются валидными.

Каждое извлечённое значение хранится записью `Extracted`. В ней есть нормализованное значение, исходный текст, уверенность, статус (`ok`, `low_confidence`, `missing`, `conflict`) и источник `SourceRef`. Источник содержит идентификатор документа, номер страницы, область в долях ширины и высоты листа, прочитанный текст, способ чтения (`text_layer`, `ocr`, `vlm`, `filename`, `rule`), уверенность, движок и его версию. У каждого расхождения Блока 1 есть код правила, важность, ожидаемое и фактическое значения, ссылки на документы, узлы дерева и области-источники. Поля отчёта описаны в [report-format.md](report-format.md).

## 6. Данные

Данные заказчика, файлы моделей и результаты прогонов в репозиторий не входят, каталоги `data/`, `models/` и `out/` исключены из git. Комплекты заказчика регистрируются под обезличенными идентификаторами вместе с ролью в разбиении и контрольными суммами файлов. В публичных материалах о них приводятся только числа под этими идентификаторами. Документы заказчика не передаются во внешние сервисы. Кэш прочтений OCR и модели включается явно и по умолчанию не хранит на диске тексты документов ([ADR-0018](adr/0018-read-cache.md)).

Листы заказчика содержат настоящие фамилии в основных надписях. Прежде чем показывать изображение листа вне этой машины, человеку или ИИ-сервису, его маскирует скрипт `eval/mask_people.py`. Он находит основную надпись по линиям бланка и закрашивает графы с фамилиями, подписями и датами, а также графы «Подп. и дата» на поле подшивки. Расположение этих граф по ГОСТ 2.104 задано в `forms.title_block.people` в `configs/forms.yaml`. Затем скрипт проверяет результат распознаванием. Сначала он читает графы подписантов всех исходных листов и собирает фамилии комплекта, они остаются только в памяти и никуда не выводятся. Потом ищет эти фамилии и любые ФИО с инициалами по всему листу, исходному и маскированному. На исходных листах проверка их находит, и это показывает, что она работает. Лист, на котором основная надпись не найдена или фамилия осталась после маскирования, не записывается и перечисляется для ручной обработки. Маскированные копии лежат в `data/arm/masked/`, вне git.

В репозитории лежат синтетический демо-комплект с эталоном (`samples/`), разметка эталона на открытых документах (`eval/gold/`), реестр открытого корпуса (`eval/open_drawings.csv`) и манифест стрессового корпуса (`eval/stress_corpus.json`). Сами открытые документы скачиваются скриптом в `data/` и сверяются по контрольным суммам.

## 8. Тестирование и непрерывная интеграция

Для каждого правила Блока 1 есть тест, в котором оно срабатывает, и тест на близкий случай, в котором оно молчит. Для ядра, API и генератора написано 617 тестов pytest, у веб-интерфейса свой набор тестов. При каждом изменении непрерывная интеграция выполняет перечисленные ниже проверки.

- Тесты на Ubuntu с Python 3.11 и 3.12 и на macOS с Python 3.11, включая сверку JSON Schema и типов веб-интерфейса с моделями контракта.
- Проверка оформления и ошибок кода (ruff), строгая проверка типов ядра (mypy) и проверка границ модулей (import-linter).
- Проверка лицензий зависимостей поставки (`scripts/check_licenses.sh`). Зависимость под AGPL останавливает сборку.
- Сборка контейнера и прогон демо-комплекта в нём.
- Проверка типов, тесты и сборка веб-интерфейса.

Команды для локального запуска тех же проверок приведены в [CONTRIBUTING.md](../CONTRIBUTING.md#commands).

## 9. Эксплуатация

Сервис поставляется одним контейнером, в который входят API, веб-интерфейс, ядро, Tesseract и распознаватель PP-OCRv5. Каждое задание выполняется отдельным процессом `kdcheck run` с лимитами времени и памяти, поэтому зависший или специально испорченный файл не останавливает API ([ADR-0006](adr/0006-job-execution.md)). Загрузка ограничена по размеру и числу файлов, чтение ограничено числом страниц на файл и размером изображения. Лимиты задаются в `configs/api.yaml` и `configs/ingest.yaml`.

В API нет входа по паролю, поэтому сервер и контейнер по умолчанию принимают соединения только с этой машины. Для доступа по сети нужен обратный прокси со входом и HTTPS. Сервер мультимодальной модели запускается отдельно. Если его нет, комплект обрабатывается одним OCR, а журнал отчёта сообщает причину.
