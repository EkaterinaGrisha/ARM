# Техническая документация

Документ описывает состав системы, устройство ядра, применяемые движки и модели, настройки, данные, воспроизведение замеров качества, тестирование и условия эксплуатации. Установка, запуск и работа с веб-интерфейсом изложены в [README](../README.md), архитектура и основания решений — в [ARCHITECTURE.md](ARCHITECTURE.md) и [docs/adr](adr), формат отчёта — в [report-format.md](report-format.md) и [report.schema.json](report.schema.json), результаты на 11.11.2026 — в [промежуточном отчёте](reports/2026-11-11-interim.md).

## 1. Состав системы

Система состоит из ядра, которое выполняет всю обработку, и оболочек над ним. API и веб-интерфейс не содержат логики проверки: они принимают комплект, запускают ядро и показывают его отчёт.

*Таблица 1. Компоненты*

| Компонент | Каталог | Назначение | Технологии |
| --- | --- | --- | --- |
| Ядро `kdcheck` | `packages/kdcheck` | Конвейер обработки, правила Блоков 1 и 2, контракт отчёта, выгрузки, командная строка `kdcheck run` | Python ≥ 3.11, pydantic, pypdfium2, Pillow, PyYAML, openpyxl; для растров и сканов — onnxruntime с numpy и Tesseract через pytesseract |
| API | `backend/arm_web` | Приём комплекта, задания, запуск ядра отдельным процессом с лимитами, выдача отчёта, выгрузок и изображений листов | FastAPI, uvicorn |
| Веб-интерфейс | `frontend` | Отчёт по комплекту, просмотр листа с подсветкой источника значения | React, TypeScript, Vite; типы отчёта генерируются из JSON Schema |
| Генератор синтетики | `synth` | Комплекты по ГОСТ с разметкой и заложенными ошибками, растры и сканы заданного качества | reportlab, pypdfium2, Pillow; Augraphy — только для сборки замороженного стрессового корпуса |
| Оценка качества | `eval` | Замеры, эталонная разметка, результаты в `eval/results` | Python |
| Настройки | `configs` | Пороги, шаблоны форм ГОСТ, словари, правила, движки, лимиты | YAML, проверка моделями pydantic |
| Промпты | `prompts` | Тексты запросов к мультимодальной модели с версиями | Текстовые файлы |

Ядро не зависит от API, генератора и оценки, а Блоки 1 и 2 не импортируют друг друга. Эти границы проверяет import-linter при каждом изменении ([ADR-0011](adr/0011-core-public-api.md)).

## 3. Движки и модели

Все движки работают на той же машине, что и ядро. Выбор движка и его параметры задаются в `configs/models.yaml`; отчёт записывает имя и версию каждого движка, а у каждого значения — движок, которым оно получено.

*Таблица 3. Движки*

| Задача | Движок | Лицензия | Когда применяется |
| --- | --- | --- | --- |
| Текстовый слой и изображения PDF | pypdfium2 (PDFium) | Apache-2.0 или BSD-3-Clause; PDFium — BSD-3-Clause | Всегда; PyMuPDF (AGPL-3.0) подключается только для отката и в поставку не входит ([ADR-0007](adr/0007-pdf-library.md)) |
| Ячейки основной надписи и строк спецификаций растров и сканов | PP-OCRv5 для восточнославянских языков через onnxruntime | Apache-2.0; onnxruntime — MIT | Если файлы модели загружены `scripts/fetch_ppocr.sh` из закреплённой ревизии ([ADR-0024](adr/0024-ppocr-cells.md)) |
| Текст листа растра и скана, резерв для ячеек | Tesseract 5, язык `rus` | Apache-2.0 | Без файлов PP-OCRv5; для текста листа вне ячеек |
| Ячейки основной надписи и строк спецификаций, блок технических требований растров и сканов | Мультимодальная модель на OpenAI-совместимом сервере; по замеру — Qwen3.6-35B-A3B | Apache-2.0 | По флагу `--vlm`; по умолчанию выключена ([ADR-0014](adr/0014-local-vlm.md), [ADR-0019](adr/0019-vlm-main-reader.md), [ADR-0021](adr/0021-vlm-spec-rows.md), [ADR-0023](adr/0023-vlm-tech-requirements.md)) |

Мультимодальная модель только читает текст вырезанной ячейки или блока. Значение нормализуют те же правила, что и для OCR, областью-источником остаётся ячейка бланка. Если прочтение модели расходится с OCR, в отчёт идёт прочтение модели со статусом `conflict`, а прочтение OCR сохраняется в заметках документа. Адрес сервера модели вне этой машины отклоняется проверкой настроек, пока в них явно не разрешена удалённая обработка; разрешение даёт только заказчик.

## 4. Настройки

Пороги, шаблоны форм, словари, правила, движки и лимиты хранятся в `configs/*.yaml` ([ADR-0012](adr/0012-configs.md)); назначение каждого файла перечислено в [README](../README.md#настройки). При запуске настройки проверяются моделями pydantic: неизвестный ключ или неверное значение останавливают обработку с указанием файла и поля. Отчёт записывает SHA-256 действующих настроек, поэтому по отчёту видно, с какими порогами он получен. Собственный набор настроек — копия каталога с правками, которая передаётся ключом `--config` или переменной `ARM_CONFIG_DIR`.

## 5. Контракт отчёта

Отчёт — модель `Report` из `kdcheck.schemas`, версия контракта 1.9. Из моделей генерируются JSON Schema ([report.schema.json](report.schema.json)) и типы TypeScript веб-интерфейса (`scripts/export_schema.sh`); тесты сверяют схему и типы с моделями. Новые поля добавляются необязательными, поэтому отчёты прежних версий остаются валидными.

Каждое извлечённое значение — запись `Extracted`: нормализованное значение, исходный текст, уверенность, статус (`ok`, `low_confidence`, `missing`, `conflict`) и источник `SourceRef`. Источник содержит идентификатор документа, номер страницы, область в долях ширины и высоты листа, прочитанный текст, способ чтения (`text_layer`, `ocr`, `vlm`, `filename`, `rule`), уверенность, движок и его версию. Каждое расхождение Блока 1 несёт код правила, важность, ожидаемое и фактическое значения, ссылки на документы, узлы дерева и области-источники. Поля отчёта описаны в [report-format.md](report-format.md).

## 6. Данные

Данные заказчика, файлы моделей и результаты прогонов в репозиторий не входят: каталоги `data/`, `models/` и `out/` исключены из git. Комплекты заказчика регистрируются под обезличенными идентификаторами с ролью в разбиении и контрольными суммами файлов; в публичных материалах приводятся только числа под этими идентификаторами. Документы заказчика не передаются во внешние сервисы. Кэш прочтений OCR и модели включается явно и по умолчанию не хранит тексты документов на диске ([ADR-0018](adr/0018-read-cache.md)).

В репозитории лежат синтетический демо-комплект с эталоном (`samples/`), разметка эталона на открытых документах (`eval/gold/`), реестр открытого корпуса (`eval/open_drawings.csv`) и манифест стрессового корпуса (`eval/stress_corpus.json`). Сами открытые документы загружаются в `data/` скриптом и сверяются по контрольным суммам.

Таблица 4 перечисляет замеры, команды для их повторения из корня репозитория и данные, которые для этого нужны. Синтетические комплекты и их разметка повторяются по сиду на любой машине; числа распознавания зависят от версий движков, поэтому они записаны в результатах.

## 8. Тестирование и непрерывная интеграция

Каждое правило Блока 1 имеет тест, где оно срабатывает, и тест на близкий случай, где оно молчит. Тесты ядра, API и генератора — 617 проверок pytest; тесты веб-интерфейса выполняет его собственный набор. Непрерывная интеграция запускает при каждом изменении:

- тесты на Ubuntu с Python 3.11 и 3.12 и на macOS с Python 3.11, в том числе сверку JSON Schema и типов веб-интерфейса с моделями контракта;
- проверку оформления и ошибок кода (ruff), строгую проверку типов ядра (mypy) и границ модулей (import-linter);
- проверку лицензий зависимостей поставки: зависимость под AGPL останавливает сборку (`scripts/check_licenses.sh`);
- сборку контейнера и прогон демо-комплекта в нём;
- проверку типов, тесты и сборку веб-интерфейса.

Команды для локального запуска тех же проверок приведены в [CONTRIBUTING.md](../CONTRIBUTING.md#commands).

## 9. Эксплуатация

Сервис поставляется одним контейнером: API, веб-интерфейс, ядро, Tesseract и распознаватель PP-OCRv5. Каждое задание выполняется отдельным процессом `kdcheck run` с лимитами времени и памяти, поэтому зависший или специально испорченный файл не останавливает API ([ADR-0006](adr/0006-job-execution.md)). Загрузка ограничена по размеру и числу файлов, чтение — по числу страниц на файл и размеру изображения; лимиты задаются в `configs/api.yaml` и `configs/ingest.yaml`.

В API нет входа по паролю, поэтому сервер и контейнер по умолчанию принимают соединения только с этой машины; доступ по сети предполагает обратный прокси со входом и HTTPS. Сервер мультимодальной модели запускается отдельно; без него комплект обрабатывается одним OCR, а журнал отчёта сообщает причину.
