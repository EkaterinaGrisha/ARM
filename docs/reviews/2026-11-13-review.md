# Обзор проекта и план работ на 13.11.2026

Дата: 13.11.2026 · Шаги плана: 2–9 · Предмет: ядро `kdcheck`, API, веб, генератор `synth`, замеры `eval/`, документы, состояние репозитория. Ветка — `feat/field-reading` с незакоммиченной работой шага 3.

Обзор дополняет [аудит 12.11.2026](2026-11-12-audit.md) и его находки не повторяет. Код не менялся. У каждой находки указано, как она проверена: прогоном или чтением кода. Правила кода для передачи — в [CODE_GUIDE.md](../CODE_GUIDE.md).

## Итог

Проект в рабочем состоянии: проверки, которые удалось запустить, проходят, исправления шага 1 в коде и тестах есть, шаг 4 сделан. Риски теперь не в коде ядра.

1. Эталон `arm-1` не начат, а от него зависят выбор пути чтения поля, калибровка, выбор конфигурации и вся оценка на реальных данных. Это единственный шаг критического пути без движения.
2. Путь чтения поля чертежа выбирается по синтетике, поле которой проще реального: надписи только горизонтальные, рамок допусков формы и двухэтажных отклонений нет. Вертикальные надписи ядро пропускает и на векторе.
3. Передача не подготовлена: быстрый старт из README не находит модели и промпты, веб-сервис не работает в Windows без Docker, файла лицензии нет, вводный документ устарел.
4. Код формально чист, но читается тяжело: несколько длинных функций, короткие имена, пояснения, которые трудно понять без ADR. Это исправляется точечно, под защитой сравнения отчётов.

## 4. План работ

Порядок — по зависимостям. Даты плана версии 3 остаются, если эталон начат не позже 15.11.

1. **Зафиксировать сделанное.** Закоммитить замер шага 3 как есть, открыть PR, подтянуть `main`. Готово, когда рабочее дерево чистое, а ветка есть в `origin`.
2. **Начать эталон `arm-1` по маскированным копиям.** Маскирование готово (`eval/mask_people.py`). Если согласование работы с листами не получено к 15.11, решить, достаточно ли маскированных копий и разметки силами тех, у кого данные уже есть. Разметку разделить по ценности:
    - обязательная, дважды: рёбра дерева с количеством, расхождения, основные надписи, строки спецификаций;
    - один раз и пятая часть повторно: пункты технических требований;
    - параметры поля — сначала на 10 чертежах деталей (пункт 3), остальные после выбора пути.
    Готово, когда обязательная часть заморожена и согласие разметок посчитано.
3. **Малый эталон поля: 10 чертежей деталей `arm-1`.** Размечаются все допуски размеров, шероховатость и допуски формы с областями. Заодно считается, какая доля надписей вертикальная, двухэтажная, в рамке. Скрипт замера шага 3 получает на вход папку комплекта и эталон и повторяет способы чтения на этих листах, прочтения — из кэша. Готово, когда у каждого способа есть F1 на реальных листах и видно, чего не хватает синтетике.
4. **Поле чертежа: решение и исправления.**
    - PP-OCRv5 на строках поля — в ядро по умолчанию: выигрыш без затрат времени. ADR, тест на срабатывание и молчание.
    - Вертикальные строки поля разбираются (Ч1); генератор рисует вертикальные размеры, чтобы потеря была видна в замере.
    - Запись модели, попавшая на строку, из которой параметр уже получен, становится вторым прочтением со статусом `conflict`, а не вторым параметром (Ч4). Запись без строки OCR не получает область в четверть листа: её либо нет в отчёте, либо она отмечена «проверить» — выбрать замером (Ч5).
    - Возврат запятой у шероховатости: сверять с полной таблицей значений стандарта, исправленное значение всегда отмечать «проверить», посчитать срабатывания на `arm-1` (Ч6).
    - В разметку поля генератора добавить значения, чтобы графа «Значение верно» считалась (Ч3).
    Модель по фрагментам остаётся настройкой профиля с моделью. Включать ли её в конфигурацию оценки, решает малый эталон.
5. **Сравнение отчётов до заморозки (М1).** Скрипт прогоняет ядро по демо-комплекту, корпусу сида 1 и `arm-1` с кэшем прочтений и сравнивает `report.json` с сохранёнными, без времени обработки. Отчёты `arm-1` хранятся вне git. Готово, когда различие в отчёте останавливает проверку и печатает, что изменилось.
6. **Вопросы АРМ письменно.** К собранным добавить: на чём будет работать сервис — Windows, Linux, есть ли GPU; как в их чертежах записывают отклонения — полем допуска, числами в два этажа или и так, и так; встречаются ли значения шероховатости вне предпочтительного ряда; кто будет сопровождать код.
7. **Калибровка, выбор конфигурации, заморозка — шаг 6 плана.** До заморозки прогнать всю оценку на `arm-1` от начала до конца теми же скриптами, что пойдут на test (М4). Заморозку отметить тегом; в `docs/EVALUATION.md` записать коммит, хэш настроек и хэш весов.
8. **Оценка — шаг 7 плана.** Интервалы — бутстрепом по комплектам и документам (М2). В ограничениях назвать, что реальный test Блока 1 — один комплект (М3). Одно правило верного извлечения: вкладка «Качество» считает через `eval/scoring.py` либо уходит из интерфейса, а качество описывает `EVALUATION.md` (З4).
9. **Чистка кода под сравнением отчётов — после замера test.** Только поведение-сохраняющие правки по списку из [CODE_GUIDE.md](../CODE_GUIDE.md): `pipeline.py`, `checks/completeness.py`, `params/critical.py`, `report/exports.py`, `backend/arm_web/evaluate.py`, общие помощники, имена. Готово, когда три контрольных отчёта совпадают с отчётами тега заморозки, а пороги сложности включены в ruff.
10. **Упаковка и передача — шаг 9 плана.**
    - Быстрый старт: `pip install -e` либо веб передаёт ядру каталоги промптов и моделей так же, как настройки. Если настроенный распознаватель ячеек не найден, это пишется в журнал отчёта, а не только в журнал сервера (З1).
    - В README — поддерживаемые системы: Linux и macOS, Windows через Docker или WSL (З2). Если АРМ нужен запуск ядра в Windows, добавить `windows-latest` в CI для `kdcheck`.
    - Файл лицензии и условия передачи согласовать с преподавателем и держателем кейса (З3).
    - `docs/HANDOVER.md` на 1–2 страницы: карта кода, запуск, как повторить оценку, четыре рецепта изменений из З5, известные ограничения.
    - ONBOARDING, README и TECHNICAL ссылаются на `EVALUATION.md` и чисел не дублируют (Р2). В PLAN остаются шаги и отметки, журнал с числами переносится в отчёты и ADR, на которые он уже ссылается (Р3).
    - Проверка на чистой машине по инструкции, человеком, который проект не запускал.

Каждый опыт — замером на малом эталоне поля и на синтетике, с критерием остановки.

| Опыт | Зачем | Мера и остановка |
| --- | --- | --- |
| Поиск строк поля детектором текста PP-OCRv5 или Tesseract в режиме разреженного текста вместо разметки страницы | 43 допуска размера пропущены, потому что строка не найдена | Доля найденных строк поля; оставить, если полнота допусков размера растёт без потери точности |
| Второй проход по листу, повёрнутому на 90° | Вертикальные размеры растров | Полнота на вертикальных надписях малого эталона |
| Рамки допусков формы — по линиям, как основная надпись: ячейка знака, значения, базы; знак — сравнением с образцами знаков ГОСТ 2.308 из `gdt_symbols` | 30 пропусков из 31 — рамка прочитана, параметр не разобран | F1 допусков формы; остановиться, если на `arm-1` рамок меньше 20 |

## 6. Что резать, если не хватает времени

По порядку: модель по фрагментам поля — в ограничения с числами; рамки допусков формы; листы документа из нескольких файлов в вебе; чистка кода дальше трёх первых модулей. Не резать: обязательную часть эталона `arm-1`, один замер test на замороженных правилах, `EVALUATION.md`, проверку запуска на чистой машине.
