# ADR-0032. Файлы комплекта с OCR читаются в нескольких процессах, отчёт от их числа не зависит

Статус: Предложено · Дата: 2026-11-20 · Этап плана: 9

## Вопрос

Как сократить время чтения комплекта, не меняя ни одного отчёта: чем делить работу, на какие части и что делать с запросами к модели? Это пункт «г» [порядка до заморозки](../PLAN.md#добавлено-1911-до-заморозки), находка У3 [аудита 12.11](../reviews/2026-11-12-audit.md).

## Контекст и ограничения

- Кейс требует пакетной проверки комплекта (CASE.md, стр. 1). Задание ограничено `job_timeout_sec` = 3600 с в `configs/api.yaml` ([ADR-0006](0006-job-execution.md)).
- Правила: один плохой файл или лист не останавливает прогон, отчёт воспроизводим, числа — в `configs/` ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: файлы и листы читаются по одному. `arm-1`, 53 листа JPG, без модели и без кэша — 92,9 с ([reading-time.md](../../eval/results/reading-time.md)).
- Факт: под профилировщиком из 197 с прогона `arm-1` чтение файлов занимает 196,8 с, разбор документов — 0,1 с. Из чтения 143 с — поиск бланка по линиям (`raster.find_corner`, код на Python), 37 с — Tesseract. Спайк 20.11, не в `eval/`.
- Факт: с моделью `arm-1` читается 630,6 с ([arm-kits-dev-vlm.md](../../eval/results/arm-kits-dev-vlm.md)), из них около 538 с, 10,1 с на лист, — запросы к модели при разборе документов. Сервер LM Studio загружен с `parallel 1` и отвечает по очереди.
- Факт: комплекты заказчика — лист в файле: `arm-1` — 53 файла на 53 листа, `arm-2` — 332 JPG ([PLAN.md](../PLAN.md#датасет-арм)). В корпусе сида 1 из 648 листов 539 векторные, 109 листов-сканов — в 98 файлах.
- Ограничение: память задания — `RLIMIT_AS` на процесс, 8 ГБ. Лист A0 при 600 dpi занимает 1,7 ГБ процесса и 2,8 ГБ Tesseract (`configs/ingest.yaml`).

Сценарии:

1. Растровый комплект из 332 листов без модели → время чтения падает в несколько раз, отчёт тот же.
2. Процесс чтения убит системой за память → прогон не падает, оставшиеся файлы читаются по одному, журнал отчёта говорит об этом.
3. Векторный комплект или прогон без OCR → процессы не запускаются.

## Варианты

- **A. Как есть.** Файлы и листы по одному в процессе задания.
- **B. Потоки в процессе задания.** Пул потоков по файлам.
- **C. Процессы по файлам.** Пул процессов `spawn` по файлам комплекта, документы собираются в порядке файлов. Копии файлов определяются до чтения по SHA-256.
- **D. Процессы по листам.** Пул процессов по страницам каждого файла.

Замер — [reading-time.md](../../eval/results/reading-time.md), Darwin arm64, 10 ядер, без модели и без кэша.

| Критерий | A | B, 4 потока | C, 4 процесса | D |
| --- | --- | --- | --- | --- |
| `arm-1`, 53 листа, с | 92,9 | 65,1 | 32,2 | не мерился |
| Корпус сида 1, 648 листов, с | 121,9 | не мерился | 62,6 | не мерился |
| Отчёты как снимок | 21 из 21 | 1 из 1 | 21 из 21 | — |
| Многостраничный скан | по одному листу | по одному | по одному | параллельно |
| Сложность | — | малая | модуль `kdcheck.ingest.kit`, 96 строк | состояние файла собирается из листов: качество скана по первому непустому листу, слой распознавания, вид входа |
| Память | один лист | один лист | лист на процесс | лист на процесс |
| Цена отмены | — | — | `processes: 1` в `configs/ingest.yaml` | — |

Потоки ускоряют только Tesseract и PP-OCRv5, которые отпускают GIL; поиск бланка на Python идёт по одному. У процессов `arm-1` читается за 50,6 с при двух, 32,2 при четырёх, 27,1 при шести и 26,7 при восьми. Корпус сида 1 ускоряется меньше: в комплекте в среднем 5 файлов со сканами, и пул запускается на каждый комплект.

Варианты B–D меняют только чтение файлов. Запросы к модели идут при разборе документов, они разобраны ниже.

## Решение

Вариант C. Файлы комплекта с OCR читают `ingest.processes` процессов, по умолчанию 4: на 10 ядрах это ускорение в 2,9 раза, а шесть процессов дают 3,4 раза при полуторной памяти. Без OCR процессы не запускаются. Процессы запускаются методом `spawn`: копия процесса задания (`fork`) унаследовала бы потоки onnxruntime в произвольном состоянии. Каждый файл читается так же, как без пула, поэтому отчёт не зависит от числа процессов, и оно не входит в хэш настроек. Процесс, который умер, стоит только времени: его файлы дочитываются по одному в процессе задания, журнал отчёта называет их число.

Запросы к модели остаются по одному. Выигрыш от параллельных запросов зависит от сервера: LM Studio принимает их, если модель загружена с `--parallel N`. Пакетная генерация может давать другие ответы, чем одиночная, поэтому параллельность вводится только по замеру времени и совпадения отчётов с моделью.

Оценка для 332 листов по числам `arm-1`: без модели — около 200 с вместо 580; с моделью — около 56 мин запросов и 3 мин чтения, у лимита задания в 60 мин. Тайм-аут задания по числу листов остаётся в шаге 9 плана.

## Последствия

- Код: `kdcheck.ingest.kit.load_kit` — пул процессов, копии файлов по SHA-256 до чтения, счётчики кэша прочтений из процессов. `load_document` получает первый файл с теми же байтами. `ingest.processes` в `configs/ingest.yaml` не входит в хэш настроек.
- Скрипт, который вызывает `kdcheck.run.run`, держит свой код под `if __name__ == "__main__":`, иначе каждый процесс выполнит его заново.
- Память: `job_memory_mb` ограничивает каждый процесс чтения отдельно, задание занимает до `processes + 1` таких лимитов.
- Тесты: пул даёт те же документы, что один процесс, копия файла узнаётся; без OCR пул не запускается; файлы умершего процесса дочитываются по одному; число процессов не меняет хэш настроек; демо-комплект с OCR при 1 и 4 процессах даёт один отчёт.
- Замер: `eval/reading_time.py` — время по числу процессов и сверка каждого отчёта со снимком.
- Принятый риск: многостраничный PDF-скан читается одним процессом.

## Когда пересмотреть

- В комплектах появятся многостраничные PDF-сканы: вариант D.
- Сервер модели загружен с `--parallel N`: замер выигрыша и совпадения отчётов с моделью.
- Машина заказчика с другим числом ядер или памяти: `processes` по её замеру.
