# ADR-0032. Файлы комплекта читают несколько процессов, документы ждут модель вместе; отчёт от их числа не зависит

Статус: Предложено · Дата: 2026-11-20 · Этап плана: 9

## Вопрос

Как сократить время чтения комплекта, не меняя ни одного отчёта: чем делить чтение файлов и как посылать запросы к модели? Это пункт «г» [порядка до заморозки](../PLAN.md#добавлено-1911-до-заморозки), находка У3 [аудита 12.11](../reviews/2026-11-12-audit.md).

## Контекст и ограничения

- Кейс требует пакетной проверки комплекта (CASE.md, стр. 1). Задание ограничено `job_timeout_sec` = 3600 с в `configs/api.yaml` ([ADR-0006](0006-job-execution.md)).
- Правила: один плохой файл или лист не останавливает прогон, отчёт воспроизводим, числа — в `configs/` ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: файлы и документы обрабатываются по одному. `arm-1`, 53 листа JPG, без кэша: без модели — 92,9 с, с моделью — 630,6 с 16.11 ([reading-time.md](../../eval/results/reading-time.md), [arm-kits-dev-vlm.md](../../eval/results/arm-kits-dev-vlm.md)).
- Факт: под профилировщиком из 197 с прогона `arm-1` без модели чтение файлов занимает 196,8 с, разбор документов — 0,1 с. Из чтения 143 с — поиск бланка по линиям (`raster.find_corner`, код на Python), 37 с — Tesseract. Спайк 20.11, не в `eval/`.
- Факт: с моделью почти всё время разбора документов — ожидание ответов: около 10 с на лист. Сервер LM Studio держит модель с `parallel 1` и считает запросы по одному.
- Факт: комплекты заказчика — лист в файле: `arm-1` — 53 файла на 53 листа, `arm-2` — 332 JPG ([PLAN.md](../PLAN.md#датасет-арм)). В корпусе сида 1 из 648 листов 539 векторные, 109 листов-сканов — в 98 файлах.
- Ограничение: память задания — `RLIMIT_AS` на процесс, 8 ГБ. Лист A0 при 600 dpi занимает 1,7 ГБ процесса и 2,8 ГБ Tesseract (`configs/ingest.yaml`).

Сценарии:

1. Растровый комплект из 332 листов → время падает в разы без модели и укладывается в лимит задания с моделью, отчёт тот же.
2. Процесс чтения убит системой за память → прогон не падает, оставшиеся файлы читаются по одному, журнал отчёта говорит об этом.
3. Векторный комплект или прогон без OCR → процессы не запускаются.

## Варианты: чтение файлов

- **A. Как есть.** Файлы и листы по одному в процессе задания.
- **B. Потоки в процессе задания.** Пул потоков по файлам.
- **C. Процессы по файлам.** Пул процессов `spawn` по файлам комплекта, документы собираются в порядке файлов. Копии файлов определяются до чтения по SHA-256.
- **D. Процессы по листам.** Пул процессов по страницам каждого файла.

Замер — [reading-time.md](../../eval/results/reading-time.md), Darwin arm64, 10 ядер, без модели и без кэша.

| Критерий | A | B, 4 потока | C, 4 процесса | D |
| --- | --- | --- | --- | --- |
| `arm-1`, 53 листа, с | 92,9 | 65,1 | 32,2 | не мерился |
| Корпус сида 1, 648 листов, с | 121,9 | не мерился | 62,6 | не мерился |
| Отчёты как снимок | 21 из 21 | 1 из 1 | 21 из 21 | — |
| Многостраничный скан | по одному листу | по одному | по одному | параллельно |
| Сложность | — | малая | модуль `kdcheck.ingest.kit`, 96 строк | состояние файла собирается из листов: качество скана по первому непустому листу, слой распознавания, вид входа |
| Память | один лист | один лист | лист на процесс | лист на процесс |
| Цена отмены | — | — | `processes: 1` в `configs/ingest.yaml` | — |

Потоки ускоряют только Tesseract и PP-OCRv5, которые отпускают GIL; поиск бланка на Python идёт по одному. У процессов `arm-1` читается за 50,6 с при двух, 32,2 при четырёх, 27,1 при шести и 26,7 при восьми. Корпус сида 1 ускоряется меньше: в комплекте в среднем 5 файлов со сканами, и пул запускается на каждый комплект.

## Варианты: запросы к модели

Запросы идут при разборе документов: ячейки основной надписи, строки спецификации, блок технических требований.

- **M1. Как есть.** Документы разбираются по одному, сервер простаивает, пока ядро готовит следующий запрос.
- **M2. Документы ждут модель вместе.** Несколько документов разбираются в потоках, каждый посылает свои запросы по порядку; сервер считает по одному.
- **M3. Сервер считает пакетом.** Как M2, но модель загружена с `--parallel 4` и считает запросы вместе.

Замер: 60 записанных запросов ядра на `arm-1` посланы снова ([vlm-parallel.md](../../eval/results/vlm-parallel.md)); прогон `arm-1` с моделью без кэша, файлы читают 4 процесса ([reading-time.md](../../eval/results/reading-time.md)).

| Критерий | M1 | M2, 4 сразу | M3, 4 сразу |
| --- | --- | --- | --- |
| 60 запросов, с | 58,9 | 50,9 | 48,9 |
| Ответы как по одному | 60 из 60 | 60 из 60 | 58 из 60 |
| `arm-1` с моделью, с | 561,0 | 504,0 | не мерился |
| Отчёт `arm-1` тот же | — | да | — |

У M3 два ответа из 60 отличаются одной буквой: «cdope» и «сdope», латинская и кириллическая «с». Ответ зависит от того, какие запросы сервер посчитал вместе, и отчёт перестал бы повторяться.

## Решение

Вариант C для файлов и M2 для модели.

Файлы комплекта с OCR читают `ingest.processes` процессов, по умолчанию 4: на 10 ядрах это ускорение в 2,9 раза, а шесть процессов дают 3,4 раза при полуторной памяти. Без OCR процессы не запускаются. Процессы запускаются методом `spawn`: копия процесса задания (`fork`) унаследовала бы потоки onnxruntime в произвольном состоянии. Каждый файл читается так же, как без пула, поэтому отчёт не зависит от числа процессов. Процесс, который умер, стоит только времени: его файлы дочитываются по одному в процессе задания, журнал отчёта называет их число.

С моделью документы разбираются в `vlm.requests_at_once` потоках, по умолчанию 4, и результаты собираются в порядке файлов. Сервер остаётся с `parallel 1`: тогда ответы те же, что по одному. Оба числа не входят в хэш настроек: они меняют время прогона, а не отчёт.

Оценка для 332 листов по числам `arm-1`: без модели — около 200 с вместо 580; с моделью — около 53 мин вместо 66 по замеру 16.11, при лимите задания 60 мин. Тайм-аут задания по числу листов остаётся в шаге 9 плана.

## Последствия

- Код: `kdcheck.ingest.kit.load_kit` — пул процессов, копии файлов по SHA-256 до чтения, счётчики кэша прочтений из процессов; `load_document` получает первый файл с теми же байтами. Разбор документа возвращает спецификацию или запись детали вместо дописывания в общие списки. PDFium в `page_raster` и счётчики кэша закрыты блокировками.
- Настройки: `ingest.processes` в `configs/ingest.yaml`, `vlm.requests_at_once` в `configs/models.yaml`; оба вне хэша настроек.
- Скрипт, который вызывает `kdcheck.run.run`, держит свой код под `if __name__ == "__main__":`, иначе каждый процесс выполнит его заново.
- Память: `job_memory_mb` ограничивает каждый процесс чтения отдельно, задание занимает до `processes + 1` таких лимитов.
- Тесты: пул даёт те же документы, что один процесс, копия файла узнаётся; без OCR пул не запускается; файлы умершего процесса дочитываются по одному; числа не меняют хэш настроек; демо-комплект с OCR при 1 и 4 процессах и с моделью-заглушкой при 1 и 4 запросах сразу даёт один отчёт.
- Замер: `eval/reading_time.py` — время по числу процессов и запросов, сверка отчётов; `eval/vlm_parallel.py` — запросы к модели по одному и вместе на стороне сервера.
- Принятые риски: многостраничный PDF-скан читается одним процессом. Если сервер перестал отвечать посреди прогона, заметку об этом получают все документы, которые в тот момент ждали ответа, а не один.

## Когда пересмотреть

- В комплектах появятся многостраничные PDF-сканы: вариант D.
- Сервер, у которого пакетные ответы совпадают с одиночными, например vLLM на GPU заказчика: повторить `eval/vlm_parallel.py`, и при 60 из 60 — вариант M3.
- Машина заказчика с другим числом ядер или памяти: `processes` по её замеру.
