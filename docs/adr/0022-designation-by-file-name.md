# ADR-0022. Обозначение основной надписи растра сверяется с обозначением в имени файла по цифрам

Статус: Принято 2026-11-11, предложено 2026-11-09 · Этап плана: 4

## Вопрос

Как ядро выбирает обозначение документа, когда основная надпись растра или скана, прочитанная OCR или моделью, расходится с обозначением в имени файла? Это остаток третьего пункта шага 3 [порядка работ](../PLAN.md#порядок-работ-до-демо): «если имя файла, основная надпись и строка спецификации расходятся, значение получает статус `conflict`». Строку спецификации со своим комплектом сверяет [ADR-0020](0020-row-designations-by-kit.md); здесь — основная надпись с именем своего файла.

## Контекст и ограничения

- Кейс: «Сопоставление позиций дерева с фактически присутствующими файлами чертежей по обозначению»; «Извлечение полей основной надписи: обозначение» (CASE.md, стр. 2). Комплекты приходят «с возможными расхождениями структуры именования файлов» (стр. 3).
- Правила: правила прежде моделей; у значения — `Evidence`; пороги — в `configs/` ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: сейчас обозначение документа берётся из основной надписи, а из имени файла — только когда надпись его не дала. Расхождение оставляет заметку, статус значения не меняется. Чертёж, чьё обозначение прочитано с ошибкой, не находит свою строку: в отчёте пропущенный чертёж и чертёж вне спецификаций.
- Факт: синтетика, 20 комплектов ([synth-kits.md](../../eval/results/synth-kits.md)), растры и сканы с обозначением в основной надписи, против разметки:
  - с OCR верны 58 обозначений из 76;
  - у 11 из 18 неверных имя файла даёт обозначение с теми же цифрами: OCR путает буквы кода организации, 9 раз читает «Л» как «П» («ПМКР» вместо «ЛМКР»). Пропущенной цифры среди них нет, а в строках спецификаций OCR теряет «1» чаще других цифр (ADR-0020);
  - у 5 цифра прочитана как другая, «1» как «4» или «7», при верном имени файла;
  - у 2 имя файла вида «обозначение_наименование»: такого имени ядро пока не разбирает, это пробел шага 5;
  - с моделью верны 78 из 80, неверные — «КТПМ» вместо «КТРМ» у двух сканов. У одного верное имя файла, у другого имя вида «обозначение_наименование»; там OCR прочёл обозначение верно.
- Факт: на `arm-1` обозначение основной надписи совпадает с именем файла у всех 53 документов с моделью, а без неё обозначения дают имена файлов ([arm-kits-dev.md](../../eval/results/arm-kits-dev.md), подсчёт только чисел).
- Ограничение: имя файла набрано человеком и тоже может быть неверным. Обозначения соседних документов отличаются одной цифрой (…001 и …002). Правило, которое всегда верит имени, скроет файл, названный обозначением соседа.

Сценарии:

1. Модель прочла «КТПМ.381146.000», файл назван «КТРМ.381146.000» → у документа обозначение из имени файла со статусом `conflict`, прочтение остаётся в `raw` и в заметке.
2. OCR прочёл «ВЕДС.71141.001», файл — «ВЕДС.711141.001» → то же: тонкую «1» OCR теряет.
3. OCR прочёл «ВЕДС.711142.001», файл — «ВЕДС.711141.001» → прочтение остаётся со статусом `conflict`: файл может быть назван неверно.
4. Текстовый слой векторного чертежа даёт «КТПМ.381146.000», файл — «КТРМ.381146.000» → прочтение остаётся со статусом `conflict`: слой — то, что написано в документе.

## Варианты

- **A. Как сейчас**: основная надпись, заметка о расхождении.
- **B. Имя файла всегда**, если основная надпись прочитана OCR или моделью.
- **C. Сверка по цифрам, как в ADR-0020.** Имя файла выбирается, если его цифры совпадают с цифрами прочтения или отличаются одной пропущенной или лишней. Буквы не сравниваются. Иначе прочтение остаётся. Любое расхождение даёт статус `conflict`.
- **D. C и строки спецификаций третьим свидетелем**: при замене цифры выбирается то из двух обозначений, которое называет строка спецификации.

| Критерий | A | B | C | D |
| --- | --- | --- | --- | --- |
| Сценарии 1 и 2 | прочтение | имя файла | имя файла | имя файла |
| Сценарий 3: файл назван обозначением соседа | прочтение | скрыт | прочтение, `conflict` | по строке; строку растра читает тот же OCR |
| Синтетика с OCR: верных обозначений растров из 76 | 58 | 74 ¹ | 69 | не мерилось |
| Синтетика с моделью: из 80 | 78 | 79 | 79 | 79 |
| Цена | — | правило | правило | второй проход по документам после строк |

¹ На синтетике нет файлов с неверным именем: генератор их не закладывает, поэтому цена B на ней не видна.

## Решение

Рекомендуем C.

- **Где.** `kdcheck.normalize.file_designation.reconcile`, вызов в `kdcheck.pipeline` там, где документ получает обозначение основной надписи: у чертежа, последующего листа и спецификации, до сборки документов из листов (ADR-0017). Тогда и листы одного документа собираются по исправленному обозначению.
- **Какие документы.** Обозначение прочитано способом из `file_designations.methods`, по умолчанию OCR и моделью, и имя файла даёт обозначение по грамматикам комплекта (ADR-0016). Если они отличаются только кодом документа, остаётся заметка, как сейчас.
- **Как.** Цифры сравниваются без кода документа; в обозначении из имени файла их не меньше `min_digits`, по умолчанию 5. Те же цифры или одна пропущенная или лишняя — документ получает обозначение из имени файла. Код документа берётся из имени файла, а без него — из прочтения. Замена цифры не допускается.
- **Отчёт.** Значение — обозначение из имени файла, `raw` — прочтение, область — ячейка основной надписи, статус — `conflict`. В заметках документа: «Основная надпись, «Обозначение документа»: прочитано «…», в имени файла «…»; в отчёте — «…»». При любом другом расхождении, в том числе у текстового слоя, остаётся прочтение со статусом `conflict` и прежняя заметка.
- **Настройки.** Раздел `file_designations` в `configs/dictionaries.yaml`: способы чтения, `min_digits`, допуск одной вставки или удаления. Общие функции сверки цифр — в `kdcheck.normalize.designations`, их использует и ADR-0020.

## Последствия

- Код: `kdcheck.normalize.file_designation`, `digits` и `one_digit_apart` в `kdcheck.normalize.designations`, вызов в конвейере вместо прежней проверки имени файла, раздел настроек и его модель.
- Тесты: сценарии 1–4, код документа из имени файла или из прочтения, исполнение, совпадение без кода, мало цифр; на конвейере — буква, которую модель путает, и цифра, прочитанная как другая.
- Замер на синтетике ([synth-kits.md](../../eval/results/synth-kits.md)), 20 комплектов. С OCR:
  - верных обозначений растров и сканов 69 из 76 вместо 58, неверных из имени файла нет;
  - полнота Блока 1 осталась 0,844, лишних срабатываний 154 вместо 167, точность 0,297 вместо 0,280;
  - ушли 17 ошибок, появились 4. Три — `B1.LITERA.001` и `B1.LITERA.002`: связанные теперь чертежи сравнивают литеры, прочитанные OCR с ошибкой. Ещё одна — `B1.ORPHAN.001` чертежа, чья строка — на форме 5, её ядро не читает: прежде этот чертёж был вне спецификаций под неверным обозначением.

  С Qwen3.6-35B-A3B:
  - верных обозначений 79 из 80 вместо 78;
  - полнота 0,870, лишних 129 вместо 128. Исправленный документ — корневая спецификация, строки её не называют. Связей в дереве не прибавилось, а её наименование, прочитанное с ошибкой, теперь сравнивается с наименованием сборочного чертежа (`B1.NAME.001`).
- Замер на `arm-1` ([arm-kits-dev.md](../../eval/results/arm-kits-dev.md), [arm-kits-dev-vlm.md](../../eval/results/arm-kits-dev-vlm.md)): без изменений — все обозначения уже совпадают с именами файлов.
- Документы: ARCHITECTURE.md — стадия 7 и строка 22 «Решений»; PLAN.md — пункт 4.2 и шаг 3. В ADR-0021 и в PLAN.md исправлен разбор новых ошибок прогона с моделью: из 12 новых обозначение основной надписи модель исказила в двух документах, остальные дают строки спецификаций и групповые документы.
- Принимаем риск: файл, названный обозначением с той же цифровой частью и другим кодом организации или с одной пропущенной цифрой, скроет расхождение. Статус `conflict` отправляет такое значение на проверку.

## Когда пересмотреть

Если ядро работает без модели, а замена цифры останется главной ошибкой OCR в обозначениях (5 из 7 оставшихся на синтетике), — вариант D. Сравнивать нужно с замером на эталоне `arm-1`, где видно, бывают ли у заказчика файлы с неверным именем. Когда ядро начнёт разбирать имена «обозначение_наименование» (шаг 5), правило охватит и их без изменений.
