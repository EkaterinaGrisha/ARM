# ADR-0009. Контракт отчёта: формат прототипа 1.0 как основа

Статус: Принято 2026-10-20 · Этап плана: 0, реализация — этап 1 · Дополнения выходят версиями 1.1 и 1.2 — [ADR-0012](0012-configs.md)

## Вопрос

Какой формат отчёта считать контрактом между ядром, API, вебом и конвейерами других команд: черновик из ARCHITECTURE.md или формат, реализованный в прототипе?

## Контекст и ограничения

- Кейс: «Отчёт в двух формах — машиночитаемой для дальнейшей интеграции и человекочитаемой для работы технолога» (CASE.md, стр. 3).
- Кейс: «по каждому извлечённому значению видно, из какого документа и какой области страницы оно получено» (стр. 3).
- Кейс: «Над каждым блоком могут работать разные команды» (стр. 2).
- Правила: сначала контракт (`kdcheck.schemas`, `schema_version`); прослеживаемость через `Evidence`; у каждой проверки `rule_id` ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: прототип реализует `Report` 1.0 (`backend/arm_web/models.py:268-279`), JSON Schema (`docs/report.schema.json`) и описание (`docs/report-format.md`). На нём построены 8 вкладок отчёта в вебе и подключение внешних конвейеров (`external.py`).
- Факт: черновик в ARCHITECTURE.md («Отчёт: контракт») нигде не реализован.

## Варианты

- **A. Реализовать черновик** из ARCHITECTURE.md и переписать веб.
- **B. Взять формат прототипа** и дополнить недостающим в версии 1.1.
- **C. Держать оба формата** и конвертер между ними.

| Критерий | A | B | C |
| --- | --- | --- | --- |
| Работы в вебе | переписать | минимум | нет |
| Прослеживаемость по правилам | да | после дополнений | да |
| Риск для других команд | высокий | низкий | путаница форматов |
| Один источник правды | да | да | нет |

## Решение

Рекомендуем B. Формат прототипа уже закрывает требования кейса к отчёту, на нём работают веб и подключение внешних конвейеров. Недостающее добавляем без поломки: новые поля необязательные, версия 1.1.

Дополнения версии 1.1:

- `Discrepancy.rule_id` вида `B1.NAME.001` — по правилу о проверках.
- `SourceRef.engine` и `engine_version` (например, `tesseract 5.5.2`), `KitInfo.engines` — по правилу о воспроизводимости.
- `Extracted.status`: `ok`, `low_confidence`, `missing`, `conflict`.
- Модели ядра запрещают неизвестные поля (`extra="forbid"`). Внешние конвейеры кладут свои данные в поле `extensions`.
- Модель задания `Job` уходит из контракта в API.
- Шкала важности: три уровня прототипа (`high`, `medium`, `low`) или четыре из черновика. Решаем после консультации с АРМ о том, какие расхождения останавливают производство.

API получает префикс `/api/v1` при выносе ядра; старые пути работают ещё один релиз. Типы TypeScript генерируются из JSON Schema (json-schema-to-typescript, MIT), CI сверяет схему с моделями.

## Последствия

- `kdcheck.schemas` — перенесённый `models.py`; на время переноса `arm_web.models` реэкспортирует его.
- ARCHITECTURE.md: раздел «Отчёт: контракт» заменить ссылкой на `docs/report-format.md` и схему, раздел «Прослеживаемость» привести к `SourceRef`.
- Фикстура `frontend/public/demo/report.json` обновляется при каждой смене версии.

## Когда пересмотреть

Если командам блоков понадобятся промежуточные данные (области, поля до нормализации). Их схемы добавляем рядом с отчётом, не ломая его.
