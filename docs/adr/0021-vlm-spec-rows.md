# ADR-0021. Модель читает основную надпись спецификации и ячейки «Обозначение» и «Наименование» её строк на растрах и сканах

Статус: Предложено · Дата: 2026-11-09 · Этап плана: 6

## Вопрос

Как прочесть строки спецификаций растров и сканов, когда OCR их не читает, а сверка с комплектом ([ADR-0020](0020-row-designations-by-kit.md)) связывает лишь часть? Решение распространяет [ADR-0019](0019-vlm-main-reader.md) на спецификации. Это продолжение третьего пункта шага 3 [порядка работ](../PLAN.md#порядок-работ-до-демо): «затем модель на вырезках строк, с замером выигрыша поверх правила».

## Контекст и ограничения

- Кейс: дерево изделия строится по спецификациям; критерий «Полнота проверки комплектности» (CASE.md, стр. 2, критерии оценки, 2).
- Правила: модель — только с измеренным выигрышем; у значения — `Evidence`; промпты — версионные файлы ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: с ADR-0019 модель читает основные надписи только чертежей. Основную надпись спецификации ядро разбирает без модели, и на `arm-1` ни у одной из 11 спецификаций обозначение не прочитано.
- Факт: строки спецификации растра OCR читает по ячейкам таблицы, найденной по линиям (`kdcheck.ocr.cells`). На `arm-1` из 64 граф обозначения грамматике отвечают 19, с комплектом совпадают 17, и то после сверки ADR-0020.
- Факт: на вырезках ячеек основной надписи Qwen3.6-35B-A3B читает верно 99 ячеек из 112, Tesseract — 49 ([отчёт о моделях](../reports/2026-11-02-models.md)).
- Ограничение: данные заказчика уходят только на сервер на этой машине (`allow_remote: false`).

## Варианты

- **A. Как сейчас**: строки читает OCR, поверх — сверка с комплектом.
- **B. Модель на ячейках строк.** Таблица находится по линиям так же, как при чтении. Ячейки «Обозначение» и «Наименование» каждой строки, которую прочёл OCR, вырезаются и даются модели. Основная надпись спецификации читается, как у чертежа. Сверка с комплектом остаётся поверх.
- **C. Модель на всей таблице**: один запрос на лист, ответ — таблица строк.
- **D. Только обозначение**, без наименования.

| Критерий | A | B | C | D |
| --- | --- | --- | --- | --- |
| Область у значения | ячейка | ячейка | лист: строку ответа не к чему привязать | ячейка |
| Запросов на строку | 0 | 2 | ≈ 0,05 | 1 |
| `B1.NAME.001` на `arm-1` | 15 | 2 | не мерилось | ≈ 15 |
| Цена | — | модуль и промпт | разбор ответа, сверка строк | как B |

## Решение

Рекомендуем B.

- **Где.** `kdcheck.vlm.spec_rows.read_rows` и вызов из конвейера для каждой спецификации, страницы которой прочитаны способом из `vlm.methods`. Основная надпись спецификации, форма 2, читается `kdcheck.vlm.title_block.read_cells`, как у чертежа.
- **Строки.** Изображение листа, с которого читал OCR, раскладывается по линиям заново. Для каждой полосы таблицы, в которой OCR прочёл строку, из ячеек граф `vlm.rows.fields` вырезается изображение внутри линий. Область значения — эта ячейка.
- **Расхождение** — как в ADR-0019: `vlm.conflict: model` берёт прочтение модели со статусом `conflict`, прочтение OCR уходит в заметки документа. Пустую ячейку модель заполняет.
- **Промпт.** Отдельный, `prompts/spec_row_cell.v1.txt`: ячейка графы спецификации по ГОСТ 2.106. В отчёт попадают обе версии промпта.
- **Включение.** Вместе с моделью: `--vlm`, `ARM_VLM=1`.

## Последствия

- Код: `kdcheck.vlm.spec_rows`, второй клиент модели в конвейере, чтение основной надписи спецификации, `vlm.rows` в `config.py` и `models.yaml`, промпт. `eval/synth_kits.py --vlm МОДЕЛЬ` добавляет прогон с моделью.
- Тесты: расхождение берёт прочтение модели с областью ячейки, `conflict: ocr` оставляет OCR, пустое наименование заполняется, без таблицы, найденной по линиям, модель не спрашивают.
- Замер на синтетике с Qwen3.6-35B-A3B ([synth-kits.md](../../eval/results/synth-kits.md), 20 комплектов, прогон с OCR против прогона с OCR и моделью):
  - полнота Блока 1 — 0,870 вместо 0,844, лишних срабатываний 128 вместо 167, точность 0,344 вместо 0,280;
  - `B1.ORPHAN.001`: найдены 17 из 17 вместо 15, лишних 35 вместо 50; `B1.MISSING.001`: лишних 66 вместо 79; `B1.NAME.001`: лишних 5 вместо 12;
  - ушли 54 ошибки, появились 12:
    - 3 — от чертежа, в основной надписи которого модель прочла «КТПМ» вместо «КТРМ»; обозначение из имени файла этого чертежа ядро не разбирает. Основную надпись против имени файла сверяет [ADR-0022](0022-designation-by-file-name.md);
    - 3 — буквы, которые модель путает в строках спецификаций: «ДМЛС» вместо «ПМЛС», «КТПМ» вместо «КТРМ»;
    - 6 — известные пробелы, которые видны теперь, когда строки прочитаны: групповые документы ГОСТ 2.113 и «БЧ» в графе «Формат».
- Замер на `arm-1` с Qwen3.6-35B-A3B ([arm-kits-dev-vlm.md](../../eval/results/arm-kits-dev-vlm.md) против [arm-kits-dev.md](../../eval/results/arm-kits-dev.md)):
  - обозначение основной надписи есть у 11 спецификаций из 11 вместо 0;
  - обозначений строк по грамматике 49 из 64 вместо 19; сверка с комплектом после модели не меняет ни одной строки, без модели меняла 17;
  - `B1.ORPHAN.001` — 6 вместо 17, `B1.NAME.001` — 2 вместо 15; появились одно `B1.MISSING.001` и одно `B1.NAME.002`;
  - корня у дерева по-прежнему нет: изделий верхнего уровня два, и одну из спецификаций ни одна прочитанная строка не называет;
  - лист читается 9,5 с вместо 1,9; 332 листа `arm-2` — около 52 минут.
- Документы: ARCHITECTURE.md — строка 21 «Решений»; PLAN.md — пункт 4.3 и этап 6.
- Принимаем риск: на каждую строку растра — два запроса к модели. Кэш прочтений (ADR-0018) снимает их при повторном прогоне.

## Когда пересмотреть

Если запросов станет слишком много для больших комплектов, сравниваем B с C на эталоне `arm-1`. Если модель прочтёт таблицу целиком с координатами строк, область значения сохранится и при C. Обозначение основной надписи, которое расходится с именем файла только буквами при тех же цифрах, решает [ADR-0022](0022-designation-by-file-name.md).
