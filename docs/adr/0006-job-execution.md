# ADR-0006. Задание выполняется в отдельном процессе, без Redis и RQ

Статус: Принято 2026-10-20 · Этап плана: 0, реализация — этап 3

## Вопрос

Как API запускает обработку комплекта: через очередь Redis + RQ (решение 6), пулом потоков, как в прототипе, или отдельным процессом на каждое задание?

## Контекст и ограничения

- Кейс: «повреждённые файлы, посторонние документы и нечитаемые сканы не прерывают обработку комплекта» (CASE.md, стр. 3). «Пакетный режим: обработка комплекта целиком без участия пользователя» (стр. 3).
- Правила: устойчивость; ядро с CLI, API только вызывает ядро ([CONTRIBUTING.md](../../CONTRIBUTING.md#engineering-rules)).
- Факт: прототип разбирает файлы в `ThreadPoolExecutor` внутри процесса API (`backend/arm_web/jobs.py:54`). Зависание или утечка памяти в PDF-библиотеке на недоверенном файле останавливает весь сервер.
- Факт: в прототипе уже есть запуск внешнего конвейера отдельным процессом с тайм-аутом (`backend/arm_web/pipeline/external.py:38-41`).
- Допущение: один сервер, единицы комплектов в день, несколько технологов.
- Ограничение: развёртывание у заказчика, возможно без интернета; чем меньше сервисов, тем проще.

## Варианты

- **A. Пул потоков в процессе API**, как сейчас.
- **B. Redis + RQ**: API ставит задачу в очередь, отдельный воркер её выполняет.
- **C. Процесс на задание**: API запускает `kdcheck run` через `subprocess` с тайм-аутом и лимитом памяти. Прогресс — в `progress.json`, состояние — в `job.json`.

| Критерий | A. Потоки | B. Redis + RQ | C. Процесс на задание |
| --- | --- | --- | --- |
| Изоляция недоверенных файлов | нет | да, в воркере | да |
| Тайм-аут и лимит памяти | нет | тайм-аут RQ; память — средствами ОС | да: тайм-аут и `resource.setrlimit` в Linux |
| Сервисов в поставке | 1 | 3: api, worker, redis | 1 |
| Веб и CLI дают одинаковый результат | да | да | да, веб вызывает тот же CLI |
| Несколько серверов | нет | да | нет; кейс этого не требует |
| Готовность в прототипе | есть | нет | почти: `external.py` |
| Цена смены решения | — | высокая | низкая: процесс легко сделать задачей воркера |

## Решение

Рекомендуем C. Он даёт изоляцию и лимиты, которых нет в A, и обходится без двух лишних сервисов B. Веб вызывает тот же CLI, поэтому результат совпадает с командной строкой. Перейти на B позже просто: запуск процесса становится задачей воркера.

## Последствия

- `jobs.py` запускает `kdcheck run` вместо `pipeline.run` в потоке; `external.py` становится общим механизмом запуска.
- Лимиты — время на комплект, память процесса, размер загрузки, число страниц — задаются в `configs/`.
- ARCHITECTURE.md: убрать Redis, RQ и SQLite из схемы компонентов и стека; решение 6 заменить этим.
- Новый тест: зависший или слишком тяжёлый файл завершает задание по тайм-ауту, сервер продолжает отвечать.

## Когда пересмотреть

Если понадобится обрабатывать больше комплектов одновременно, чем выдерживает один сервер, или появится требование распределённой обработки.
