# ADR-0010. Структура репозитория и граница ядра

Статус: Предложено · Дата: 2026-10-20 · Этап плана: 0, реализация — этапы 1–3

## Вопрос

Где живёт ядро и как разложить репозиторий, чтобы команды Блока 1, Блока 2 и веба работали независимо, а прототип не ломался?

## Контекст и ограничения

- Кейс: «Над каждым блоком могут работать разные команды» (CASE.md, стр. 2). Прототип — «приложение или инструмент командной строки: на входе — папка с комплектом, на выходе — отчёт» (стр. 3).
- Правила: ядро `kdcheck` с CLI, API и веб только вызывают ядро; небольшие PR ([CONTRIBUTING.md](../../CONTRIBUTING.md)).
- Факт: прототип состоит из `backend/arm_web` (API, задания, конвейер, выгрузки, оценка, генератор), `frontend/` и `samples/`.
- Факт: API импортирует внутренности конвейера (`backend/arm_web/main.py:29`, `render.py:11`). Конвейер — один метод `BaselinePipeline.run` (`pipeline.py:48-116`).
- Факт: веб-разработчик работает в `frontend/`.
- Цель в ARCHITECTURE.md («Структура репозитория»): `packages/kdcheck`, `services/api`, `services/worker`, `web/`, `synth/`, `eval/`, `configs/`, `prompts/`, `fixtures/`.

## Варианты

- **A. Сразу на целевую структуру**: переименовать и разнести всё одним PR.
- **B. По шагам**: добавить `packages/kdcheck` и переносить модули по одному. `backend/` становится тонким API, `frontend/` не трогаем. Новые каталоги создаём, когда в них появляется код.
- **C. Оставить `arm_web`** как есть и следить за границами внутри пакета.

| Критерий | A | B | C |
| --- | --- | --- | --- |
| Риск поломки | высокий | низкий | нет |
| Ядро ставится отдельно | да | да | нет |
| Независимость команд блоков | да | да, по мере переноса | слабая |
| Изменения для веб-команды | пути, сборка, Docker | нет | нет |
| Объём | L | M, частями | S |

## Решение

Рекомендуем B. Он приводит к целевой границе ядра, но каждый шаг — небольшой PR, после которого приложение работает. Переименования `frontend/` → `web/` и `backend/` → `services/api/` пользы не дают, поэтому меняем архитектуру, а не код.

Целевая раскладка:

```
packages/kdcheck/   ядро: schemas, ingest, layout, extract, normalize, tree, checks, params, report, cli
backend/            API: FastAPI, задания, раздача веба
frontend/           веб
configs/            шаблоны ГОСТ, пороги, словари, модели
synth/              генератор синтетики
eval/               эталон, метрики, разбор ошибок
samples/            демо-комплект, он же фикстура тестов
```

Корневой `pyproject.toml` — uv workspace из `packages/kdcheck` и `backend`.

Границы проверяются автоматически. import-linter (BSD-2-Clause) в CI не даёт `backend` импортировать из `kdcheck` ничего, кроме публичного API: `kdcheck.schemas`, `kdcheck.run`, `kdcheck.render`. Внутри ядра Блок 1 (`tree`, `checks`) и Блок 2 (`params`) не импортируют друг друга.
