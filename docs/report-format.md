# Формат отчёта (`report.json`)

Отчёт — контракт между конвейером обработки и веб-интерфейсом. Любая реализация
блоков 1 и 2 (OCR, VLM, LLM, правила), которая пишет `report.json` в этом формате,
отображается в интерфейсе без изменений фронтенда.

* Модели: [`kdcheck.schemas`](../packages/kdcheck/src/kdcheck/schemas/report.py) (Pydantic)
* JSON Schema: [`report.schema.json`](report.schema.json) — генерируется из моделей
* Типы TypeScript: [`frontend/src/api/report.generated.ts`](../frontend/src/api/report.generated.ts) — генерируются из схемы

Схема и типы обновляются одной командой `sh scripts/export_schema.sh`. Тесты падают, если схема отстала от моделей или типы — от схемы.
* Пример: [`frontend/public/demo/report.json`](../frontend/public/demo/report.json)

Версия формата — поле `schema_version` (сейчас `1.0`). Необязательные поля можно
опускать; неизвестные поля сохраняются (модели допускают расширение).

## Прослеживаемость

Каждое извлечённое значение несёт ссылку на источник `SourceRef`:

```json
{
  "document_id": "d30d4d43f1d",
  "page": 1,
  "bbox": [0.7641, 0.8058, 0.9268, 0.8435],
  "text": "АРМ.303411.000 СБ",
  "method": "text_layer",
  "confidence": 0.95
}
```

* `bbox` — область `[x0, y0, x1, y1]` в **долях** ширины и высоты страницы, начало
  координат в левом верхнем углу. Так область не зависит от разрешения растра и
  одинаково работает для векторных PDF и сканов.
* `method` — `text_layer` (текстовый слой PDF), `ocr`, `vlm`, `llm`, `filename`
  (из имени файла), `rule`, `manual`. Интерфейс помечает значения из `ocr` и
  `filename`, а также с `confidence < 0.6`, как требующие проверки.

Значение поля — `Extracted`: `{value, raw, confidence, source}`, где `raw` — исходный
распознанный текст, `value` — нормализованное значение.

## Разделы

| Поле | Содержимое |
|---|---|
| `kit` | идентификатор, название, изделие верхнего уровня, время и длительность обработки, конвейер |
| `summary` | счётчики для сводки: документы по статусам и типам, расхождения по типам, укомплектованность |
| `documents` | все файлы комплекта: путь, страницы и их размеры, тип, происхождение (вектор/скан), статус, пояснение |
| `specifications` | разобранные спецификации: поля основной надписи и строки (раздел, формат, зона, поз., обозначение, наименование, кол., примечание) |
| `tree` | дерево изделия: узлы с видом, количеством (в т. ч. на изделие), ссылками на спецификацию и чертежи, статусом и расхождениями |
| `discrepancies` | расхождения блока 1 с типом, важностью, ожидаемым/фактическим значением, документами и источниками |
| `parts` | данные чертежей блока 2: основная надпись, пункты ТТ, параметры в единой структуре |
| `critical_parameters` | параметры, потенциально критичные для производства, с правилом и обоснованием |
| `quality` | необязательно: метрики по эталону, разбор ошибок, ограничения |
| `log` | замечания конвейера |

### Статусы документов (`documents[].status`)

| Статус | Смысл |
|---|---|
| `ok` | прочитан и разобран |
| `warning` | обработан частично (скан без OCR, не найдена основная надпись…), см. `problem` |
| `damaged` | файл повреждён или пуст |
| `unreadable` | скан низкого качества: распознавание невозможно |
| `foreign` | посторонний документ: нет основной надписи чертежа и граф спецификации |
| `unsupported` | формат не PDF и не изображение |

### Типы расхождений (`discrepancies[].type`)

| Тип | Когда |
|---|---|
| `missing_drawing` | позиция есть в спецификации (раздел «Детали» или документ из «Документации»), а чертежа в комплекте нет; позиции с примечанием «БЧ» не проверяются |
| `missing_specification` | сборочная единица указана, но её спецификации нет — раскрыть состав невозможно |
| `orphan_drawing` | чертёж есть в комплекте, но не входит ни в одну спецификацию |
| `name_mismatch` | наименование на чертеже (или в собственной спецификации СЕ) отличается от наименования в спецификации; сравнение без учёта регистра, «ё/е» и пунктуации |
| `duplicate_designation` | одно обозначение у нескольких документов (кроме листов многолистового документа) или у разных позиций спецификаций |
| `revision_mismatch` | в комплекте разные версии документа (номер изменения или литера), литеры спецификации и её сборочного чертежа различаются, литера составной части ниже литеры изделия |

### Параметры (`parts[].parameters`)

Единая структура для сравнения деталей и загрузки в учётные системы:

| Поле | Пример |
|---|---|
| `category` | `dimension_tolerance`, `general_tolerance`, `roughness`, `geometric`, `heat_treatment`, `hardness`, `coating`, `other` |
| `name` | `Ø50k6`, `Ra 0,8`, `↗ биения`, `Твёрдость HRC`, `Цементация` |
| `value` / `value_min` / `value_max`, `unit` | `0.8 мкм`; `58…62 HRC`; глубина слоя `0,8…1,2 мм` |
| `qualifier` | поле допуска `k6`, шкала `HRC`, базы `А-Б`, код покрытия |
| `it_grade` | квалитет (6 для `k6`, 14 для общих допусков) |
| `general` | общее требование: неуказанные предельные отклонения, шероховатость остального |
| `critical` | отмечен как критичный |
| `text`, `source` | исходный текст и место на странице |

### Правила отбора критичных параметров (`critical_parameters[].rule`)

| Правило | Критерий |
|---|---|
| `tight_fit` | квалитет IT6 и точнее |
| `fine_roughness` | Ra ≤ 0,8 мкм (Rz ≤ 6,3); отмечается минимальное значение в комплекте |
| `high_hardness` | твёрдость ≥ 45 HRC |
| `chemical_heat_treatment` | цементация, нитроцементация, азотирование |
| `tight_geometric` | допуск формы/расположения ≤ 0,02 мм |
| `rare_in_kit` | покрытие встречается у одной детали комплекта |

Обоснование (`reason`) включает положение значения в распределении по комплекту
(«точнее 69 % посадочных размеров комплекта»), оценка `score` 0–1 задаёт порядок разбора.
