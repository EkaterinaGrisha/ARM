# Формат отчёта (`report.json`)

Отчёт — контракт между конвейером обработки и веб-интерфейсом. Любая реализация
блоков 1 и 2 (OCR, VLM, LLM, правила), которая пишет `report.json` в этом формате,
отображается в интерфейсе без изменений фронтенда.

* Модели: [`kdcheck.schemas`](../packages/kdcheck/src/kdcheck/schemas/report.py) (Pydantic)
* JSON Schema: [`report.schema.json`](report.schema.json) — генерируется из моделей
* Типы TypeScript: [`frontend/src/api/report.generated.ts`](../frontend/src/api/report.generated.ts) — генерируются из схемы

Схема и типы обновляются одной командой `sh scripts/export_schema.sh`. Тесты падают, если схема отстала от моделей или типы — от схемы.
* Пример: [`frontend/public/demo/report.json`](../frontend/public/demo/report.json)

Версия формата — поле `schema_version` (сейчас `1.9`). Необязательные поля можно
опускать. Неизвестные поля модели отклоняют, чтобы опечатка в имени поля не прошла
незамеченной; свои данные внешний конвейер кладёт в `extensions`. Отчёты прежних версий
остаются валидными: каждая версия добавляла только необязательные поля (таблица ниже).

| С версии | Поле | Содержимое |
|---|---|---|
| 1.1 | `kit.engines` | движки и библиотеки, от которых зависит результат: `[{"name": "pdfium", "version": "156.0.8076.0"}, …]` |
| 1.1 | `kit.config_sha256` | SHA-256 настроек `configs/*.yaml`, с которыми получен отчёт: одинаковый хэш — одинаковые пороги, шаблоны и словари |
| 1.1 | `SourceRef.engine`, `SourceRef.engine_version` | движок, прочитавший текст значения, и его версия: `pdfium`, `tesseract` |
| 1.2 | `discrepancies[].rule_id` | правило, которое нашло расхождение: `B1.NAME.001` (раздел «Правила Блока 1») |

## Прослеживаемость

Каждое извлечённое значение несёт ссылку на источник `SourceRef`:

```json
{
  "document_id": "d30d4d43f1d",
  "page": 1,
  "bbox": [0.7641, 0.8058, 0.9268, 0.8435],
  "text": "АРМ.303411.000 СБ",
  "method": "text_layer",
  "confidence": 0.95,
  "engine": "pdfium",
  "engine_version": "156.0.8076.0"
}
```

* `bbox` — область `[x0, y0, x1, y1]` в **долях** ширины и высоты страницы, начало
  координат в левом верхнем углу. Так область не зависит от разрешения растра и
  одинаково работает для векторных PDF и сканов.
* `method` — `text_layer` (текстовый слой PDF), `ocr`, `vlm`, `llm`, `filename`
  (из имени файла), `rule`, `manual`.
* `engine`, `engine_version` — чем прочитан текст; у значений из имени файла их нет.

Значение поля — `Extracted`: `{value, raw, confidence, status, source}`, где `raw` — исходный
распознанный текст, `value` — нормализованное значение, `status` — статус значения (с версии 1.2):

| Статус | Смысл |
|---|---|
| `ok` | значение принято |
| `low_confidence` | проверить по документу: прочитано способом из списка `review.methods` или с уверенностью ниже `review.min_confidence` ([`configs/ingest.yaml`](../configs/ingest.yaml); по умолчанию — `ocr`, `filename` и уверенность ниже 0,6) |
| `missing` | значения нет; `source` показывает, где его искали |
| `conflict` | источники дают разные значения; базовый конвейер ставит его ячейке основной надписи, где прочтения OCR и модели разошлись: в значении — прочтение модели, прочтение OCR — в заметках документа ([ADR-0019](adr/0019-vlm-main-reader.md)) |

Интерфейс подчёркивает значения `low_confidence` и `conflict` как требующие проверки. В отчётах
до версии 1.2 статуса нет, и интерфейс такие значения не отмечает.

## Разделы

| Поле | Содержимое |
|---|---|
| `kit` | идентификатор, название, изделие верхнего уровня, время и длительность обработки, конвейер, движки с версиями, хэш настроек |
| `summary` | счётчики для сводки: документы по статусам и типам, расхождения по типам, укомплектованность |
| `documents` | все файлы комплекта: путь, страницы и их размеры, тип, происхождение (вектор/скан), статус, пояснение |
| `specifications` | разобранные спецификации: поля основной надписи и строки (раздел, формат, зона, поз., обозначение, наименование, кол., примечание) |
| `tree` | дерево изделия: узлы с видом, количеством (в т. ч. на изделие), ссылками на спецификацию и чертежи, статусом и расхождениями |
| `discrepancies` | расхождения блока 1 с правилом, типом, важностью, ожидаемым/фактическим значением, документами и источниками |
| `parts` | данные чертежей блока 2: основная надпись, пункты ТТ, параметры в единой структуре |
| `critical_parameters` | параметры, потенциально критичные для производства, с правилом и обоснованием |
| `quality` | необязательно: метрики по эталону, разбор ошибок, ограничения |
| `log` | замечания конвейера |
| `extensions` | данные внешних конвейеров по имени конвейера |

### Страницы (`documents[].pages`)

| Поле | Содержимое |
|---|---|
| `number` | номер страницы, начиная с 1 |
| `width`, `height`, `unit` | размер страницы: `pt` у PDF, `px` у изображений; 0 — страница не открылась, размер неизвестен |
| `has_text` | у страницы есть текст: текстовый слой или результат OCR |
| `format` | формат листа по ГОСТ 2.301 (с версии 1.3) |
| `problem` | почему страница не прочитана или не разобрана (с версии 1.3) |

Формат определяется по размеру страницы в любой ориентации: основные форматы, А5 и дополнительные
(`A4x3`, `A3x3`…). Таблица форматов и допуск — в [`configs/forms.yaml`](../configs/forms.yaml): каждая
сторона может отличаться от формата не больше чем на 3 %. Размер страницы PDF известен всегда, у
изображения — только с разрешением в метаданных; без него, или если размер не подходит ни к одному
формату, `format` нет.

Сбой одной страницы не останавливает файл: страница получает `problem` и размер 0, если не открылась,
остальные страницы читаются и разбираются, а документ получает статус `warning` и пояснение со списком
страниц. Файл, у которого не прочитана ни одна страница, — `damaged`.

Лист, который читается дольше `page_timeout_sec` из `configs/ingest.yaml`, останавливается и получает
`problem` «лист читался дольше N с и не дочитан»; остальные листы и файлы читаются.

Кадр файла изображения, у которого пикселей больше `max_image_pixels` из `configs/ingest.yaml`, не
декодируется: размер страницы берётся из заголовка, `problem` — «изображение W×H пикс. (N Мп) больше M Мп и не
читается», остальные кадры читаются. Файл, у которого все кадры больше лимита, — `unsupported`. Страница PDF с
таким изображением, во вложенной форме или во внешнем виде аннотации тоже, не читается, даже если у неё есть
текстовый слой: размер страницы — её собственный, в пунктах, `problem` называет наибольшее изображение. PDF, у
которого такова каждая страница, — `unsupported`.

### Документ из нескольких файлов (`documents[].sheet`, `documents[].sheet_of`)

Комплект может хранить многолистовой документ по листу в файле, номер листа — в скобках в конце имени:
«Рама (1).jpg», «Рама (2).jpg». Файлы — листы одного документа, если у них одно обозначение, один вид
документа и разные номера листов ([ADR-0017](adr/0017-sheet-assembly.md)). Номер листа берётся из основной
надписи: графы «Лист», а без неё форма 1 или 2 означает лист 1; если надпись номера не даёт — из имени файла.
Файл с номером больше 1 сводится с документом, только если на нём найдена форма 2а последующего листа: номер
«(2)» в имени получает и копия файла. Файл без номера — лист 1, если в документе нет файла с номером 1.

`documents` по-прежнему перечисляют файлы. У последующего листа `sheet_of` — id файла первого листа.
Спецификация и запись детали (`specifications`, `parts`) — одна на документ, по файлу первого листа; в них
строки и параметры всех листов, и у каждого значения `SourceRef.document_id` называет свой файл. Файлы с одним
обозначением и одним номером листа не сводятся: их называет `B1.DUP.001` или `B1.DUP.003`, журнал — почему.

### Групповая спецификация (`specifications[].variants`, `rows[].quantities`, `rows[].variant`)

Групповая спецификация по варианту Б ГОСТ 2.113 (формы 1 и 1а — А4 альбомный, до десяти исполнений на листе;
форма 5 — до трёх) вместо графы «Кол.» отводит графу каждому исполнению. Над графой — номер исполнения: «–» у
базового, затем «01», «02»… ([ADR-0025](adr/0025-group-spec-variant-b.md)). `variants` перечисляет эти номера в
порядке граф. У строки `quantity` пуст, а `quantities` даёт количество по номеру исполнения; у документа —
«×». Обозначение исполнения — обозначение спецификации с номером через дефис: `АБВГ.301261.001-01`.

Строка, где вместо обозначения написано «-03» под строкой с полным обозначением того же изделия (ГОСТ 2.113,
п. 5.3), получает полное обозначение `…-03`, а написанное остаётся в `raw`. В дереве исполнение без своей
спецификации раскрывается по групповой спецификации базового обозначения: его позиции — строки с количеством в
его графе. Исполнение детали без своего чертежа изображено на групповом чертеже базы, у которого в графе
«Масса» — «См. табл.».

По варианту А (ГОСТ 2.113, п. 5.5.1) групповая спецификация выполнена на форме 1: сначала постоянные данные, общие
для всех исполнений, затем заголовок «Переменные данные для исполнений» и под обозначением каждого исполнения — его
строки со своими разделами ([ADR-0026](adr/0026-group-spec-variant-a.md)). У строки переменных данных `variant` —
номер исполнения из заголовка над ней («–» у базового), количество — в `quantity`; у постоянных данных `variant`
пуст. `variants` перечисляет исполнения по заголовкам в их порядке. В дереве исполнение берёт постоянные строки и
строки своего номера.

### Статусы документов (`documents[].status`)

| Статус | Смысл |
|---|---|
| `ok` | прочитан и разобран |
| `warning` | обработан частично (скан без OCR, не найдена основная надпись…), см. `problem` |
| `damaged` | файл повреждён или пуст |
| `encrypted` | PDF защищён паролем, без пароля не прочитать (с версии 1.2; раньше — `damaged`) |
| `unreadable` | скан низкого качества: распознавание невозможно |
| `blank` | все листы файла пусты: на них нет ни текста, ни линий, только бумага с пятнами, тенью или дырами переплёта (с версии 1.5). Пустой лист внутри документа — `pages[].problem`, статус файла от него не меняется |
| `foreign` | посторонний документ: нет основной надписи чертежа и граф спецификации |
| `unsupported` | формат не PDF и не изображение, или изображение больше лимита `max_image_pixels` из `configs/ingest.yaml` в каждом кадре файла изображения или на каждой странице PDF: оно не декодируется, `problem` называет его размер и лимит |
| `duplicate_file` | побайтовая копия другого файла комплекта, `problem` называет его; копия не разбирается и не даёт расхождения `duplicate_designation` (с версии 1.2) |

### Типы расхождений (`discrepancies[].type`)

| Тип | Когда |
|---|---|
| `missing_drawing` | позиция есть в спецификации (раздел «Детали» или документ из «Документации»), а чертежа в комплекте нет; позиции с «БЧ» в графе «Формат» или в примечании не проверяются |
| `missing_specification` | сборочная единица указана, но её спецификации нет — раскрыть состав невозможно |
| `orphan_drawing` | чертёж есть в комплекте, но не входит ни в одну спецификацию |
| `name_mismatch` | наименование на чертеже (или в собственной спецификации СЕ) отличается от наименования в спецификации; сравнение без учёта регистра, «ё/е» и пунктуации |
| `duplicate_designation` | одно обозначение у нескольких документов (кроме листов многолистового документа) или у разных позиций спецификаций |
| `sheets_missing` | у документа меньше листов, чем называет «Листов» его первого листа, или в нумерации листов пропуск (с версии 1.4) |
| `revision_mismatch` | в комплекте разные версии документа (номер изменения или литера), литеры спецификации и её сборочного чертежа различаются, литера составной части ниже литеры изделия |
| `format_mismatch` | графа «Формат» строки называет другой формат, чем у листов документа, обозначение которого записано в строке (с версии 1.8) |
| `section_mismatch` | сборочная единица записана в разделе «Детали» или деталь — в «Сборочных единицах» (с версии 1.8) |
| `position_anomaly` | номер позиции повторяется в спецификации, или у составной части нет количества (с версии 1.8) |
| `first_use_mismatch` | «Перв. примен.» документа называет сборочную единицу комплекта, в спецификации которой документа нет; информационно (с версии 1.8) |

Расхождения «документ отсутствует», «нет спецификации» и «документ не входит ни в одну спецификацию» бывают
предварительными, `preliminary` (с версии 1.8): в комплекте есть документы, которые ядро не прочитало, и искомый
может быть среди них. Для отсутствующего документа и спецификации это нечитаемые, повреждённые и зашифрованные
файлы, файлы неопределённого вида и документы без обозначения; для документа вне спецификаций — спецификации без
прочитанных строк. Сообщение называет первые из них (`preliminary.listed` в `configs/checks.yaml`), `document_ids` —
все.

### Правила Блока 1 (`discrepancies[].rule_id`)

Каждое расхождение находит одно правило, его код — в `rule_id`, заголовок — в `title`. Логика и тексты правил —
в [`kdcheck.checks`](../packages/kdcheck/src/kdcheck/checks/rules.py), включение и важность — в
[`configs/checks.yaml`](../configs/checks.yaml), ниже — значения по умолчанию. На каждое правило есть тест,
где оно срабатывает, и тест на близкий случай, где оно молчит.

| Правило | Тип | Важность | Когда срабатывает |
|---|---|---|---|
| `B1.MISSING.001` | `missing_drawing` | высокая | у позиции раздела «Детали» нет чертежа в комплекте; позиции с «БЧ» в графе «Формат» (ГОСТ 2.106) или в примечании не проверяются. На растре и скане OCR читает буквы «БЧ» узкой графы как цифры: «Б4», «64», «54» тоже значат «БЧ» — формат ГОСТ 2.301 всегда начинается с «А» |
| `B1.MISSING.002` | `missing_drawing` | высокая | документа из раздела «Документация», например сборочного чертежа, нет в комплекте |
| `B1.SPEC.001` | `missing_specification` | высокая | у сборочной единицы нет своей спецификации, состав не раскрыть; и у сборочного чертежа, которого не называет ни одна спецификация, — как в комплекте без спецификаций |
| `B1.ORPHAN.001` | `orphan_drawing` | средняя | документ комплекта не указан ни в одной спецификации; сборочный чертёж указанной сборочной единицы в комплект входит |
| `B1.NAME.001` | `name_mismatch` | средняя | наименование на чертеже отличается от спецификации без учёта регистра, «ё/е» и пунктуации; у значений, прочитанных OCR или моделью, ещё и больше допуска `names` в `configs/checks.yaml` |
| `B1.NAME.002` | `name_mismatch` | средняя | собственная спецификация сборочной единицы называет её иначе, чем вышестоящая; допуск тот же |

| `B1.DUP.002` | `duplicate_designation` | высокая | одно обозначение у позиций спецификаций с разными наименованиями; допуск тот же |

### Параметры (`parts[].parameters`)

Единая структура для сравнения деталей и загрузки в учётные системы:

| Поле | Пример |
|---|---|
| `category` | `dimension_tolerance`, `general_tolerance`, `roughness`, `geometric`, `heat_treatment`, `hardness`, `coating`, `other` |
| `name` | `Ø50k6`, `Ra 0,8`, `↗ биения`, `Твёрдость HRC`, `Цементация` |
| `value` / `value_min` / `value_max`, `unit` | `0.8 мкм`; `58…62 HRC`; глубина слоя `0,8…1,2 мм`; у размера с допуском `value` — номинал, `value_min`, `value_max` — предельные размеры: `Ø40H7` — 40, 40, 40,025 |
| `lower_deviation` / `upper_deviation` | предельные отклонения размера, мм (с версии 1.9): у поля допуска — по ГОСТ 25346 для размеров до 500 мм, `Ø40H7` → 0 и +0,025, `Ø40k6` → +0,002 и +0,018; у записи `Ø50±0,1` — −0,1 и +0,1. Поля, которых нет в таблицах `configs/tolerances.yaml` (`r6`, `K9`, резьба), отклонений не получают |
| `qualifier` | поле допуска `k6`, шкала `HRC`, базы `А-Б`, код покрытия |
| `it_grade` | квалитет (6 для `k6`, 14 для общих допусков) |
| `general` | общее требование: неуказанные предельные отклонения, шероховатость остального |
| `critical` | отмечен как критичный |
| `text`, `source` | исходный текст и место на странице |

Таблица «деталь × параметр» для учётных систем выгружается и отдельно, в `report.csv` (с версии 1.9): строка на
параметр детали, графы — как на листе «Параметры» выгрузки Excel, с предельными отклонениями. Разделитель — запятая,
десятичный знак — точка, кодировка UTF-8 с меткой порядка байтов, чтобы электронная таблица прочла кириллицу. Текст
из документа, который начинается как формула («=», «+», «-», «@»), получает спереди «'». `kdcheck run` пишет файл
рядом с `report.json`, API отдаёт его по `/api/jobs/{id}/report.csv`.

### Правила отбора критичных параметров (`critical_parameters[].rule`)

Пороги — в [`configs/criticality.yaml`](../configs/criticality.yaml), ниже — значения по умолчанию.

| Правило | Критерий |
|---|---|
| `tight_fit` | квалитет IT6 и точнее |
| `fine_roughness` | Ra ≤ 0,8 мкм (Rz ≤ 6,3); отмечается минимальное значение в комплекте |
| `high_hardness` | твёрдость ≥ 45 HRC |
| `chemical_heat_treatment` | цементация, нитроцементация, азотирование |
| `tight_geometric` | допуск формы/расположения ≤ 0,02 мм |
| `rare_in_kit` | покрытие встречается у одной детали комплекта |
| `kit_tail` | значение в «хвосте» комплекта: квалитет, Ra, допуск формы и расположения или твёрдость HRC среди 10 % самых жёстких значений признака и жёстче медианы, хотя порогов правил выше не переходит; признак проверяется, если в комплекте не меньше 10 его значений (с версии 1.9) |

Обоснование (`reason`) включает положение значения в распределении по комплекту
(«точнее 69 % посадочных размеров комплекта»), оценка `score` 0–1 задаёт порядок разбора.
