# Мультимодальные модели: что проверено и что получилось

02.11.2026. Цифры — из `eval/results/vlm-bench.md` и `eval/results/vlm-title-block.md`, свежая версия бенчмарка — на ветке `exp/vlm-bench-models`.

## Коротко

- Читать основную надпись с целого реального листа умеет только большая модель: Qwen3.6-27B верно читает 40 полей из 50. Tesseract — ни одного: только 13 значений есть где-то в его тексте, по полям они не разобраны.
- На вырезках — блок ТТ, одна ячейка основной надписи — Qwen3.8-27B так же точна, как Qwen3.6-27B, и в 1,6 раза быстрее.
- Маленькие модели (Gemma 4 E4B, Qianfan-OCR, PaddleOCR-VL) хорошо читают вырезки, но на целом листе почти не находят поля.
- Всё работает локально, документы никуда не уходят.

## Как модели встроены в проект

- В ядре `kdcheck` весов модели нет. Модель запущена на локальном сервере с OpenAI-совместимым API — у нас это LM Studio на Mac, `http://127.0.0.1:1234/v1` ([ADR-0014](../docs/adr/0014-local-vlm.md)). Тот же код работает с llama.cpp, Ollama, vLLM.
- Что делает модель в ядре сейчас: дочитывает ячейки основной надписи сканов, которые OCR оставил пустыми. С `verify: true` она перечитывает и заполненные ячейки; если её значение расходится с OCR, ячейка получает статус `conflict`.
- По умолчанию модель выключена: `vlm.enabled: false` в `configs/models.yaml`, включается флагом `kdcheck run --vlm` или переменной `ARM_VLM=1`. Сервер на другой машине запрещён (`allow_remote: false`).
- Каждое значение модели в отчёте помечено: метод `vlm`, имя модели, хэш промпта, пометка «проверить». Промпты лежат версионными файлами в `prompts/`.
- Замеры:
  - `eval/vlm_title_block.py` — ядро с моделью и без неё на синтетических сканах;
  - `eval/vlm_bench.py` — сами модели на одних и тех же картинках, без ядра.

## Почему эти модели

- **Локальные.** Документы заказчика нельзя отправлять во внешние API.
- **Влезают в память.** У Mac 32 ГБ на всё, поэтому берём веса до 20 ГБ в 4-битной квантизации (сжатие весов до 4 бит).
- **Свободные лицензии.** У всех проверенных моделей Apache-2.0. Модели под AGPL и проприетарными лицензиями не берём.
- **Два класса моделей, у каждого своя роль.**
  - Общие мультимодальные модели (VLM) понимают макет листа и отвечают по JSON-схеме, но они большие и медленные.
  - Документные OCR-модели маленькие и быстрые, они переводят картинку в текст, а поля в нём не выделяют.

## Как устроен бенчмарк

Модели загружаются на сервер по одной: однажды две модели на одном сервере сорвали прогон. Температура 0, сид фиксирован, ответы сохраняются, поэтому пересчёт идёт без сервера. Задач три:

1. **Листы.** 17 реальных сканов открытых альбомов: электровоз ВЛ60 1963 года, станок ИЖ-250, приборы. Бланки там до ЕСКД, часть надписей от руки. Лист подаётся целиком, длинная сторона — 2000 пикселей. Модель возвращает 6 полей: обозначение, наименование, материал, массу, масштаб, литеру. 17 × 6 = 102 поля, из них на листах заполнены 50, остальные 52 пустые.
2. **ТТ.** 30 блоков технических требований синтетических растров и сканов, вырезанных по разметке. Текст модели разбирает парсер ядра. Сравниваются 61 параметр четырёх категорий, которые пишутся только в ТТ: общие допуски, термообработка, твёрдость, покрытие.
3. **Ячейки.** 112 ячеек основной надписи 20 синтетических документов, тоже вырезанных по разметке.

Значения сравниваются после нормализации из `eval/gold.py`: регистр, «ё», десятичная запятая, пробелы, похожие латинские буквы, тире, кавычки.

## Что значит каждое число

| Столбец | Что считает | Лучше, когда |
| --- | --- | --- |
| Листы: верно | из 50 заполненных полей — сколько модель вернула ровно в нужном поле. Только для ответа по JSON-схеме | больше |
| в тексте | правильное значение целиком есть где-то в ответе. Для OCR-моделей и Tesseract это единственная мера, и она завышена: значение ещё надо найти в тексте | больше |
| выдумано | из 52 полей, которых на листе нет, — сколько модель всё равно заполнила | меньше |
| ТТ: параметры | из 61 параметра — сколько найдено с верной категорией и названием | больше |
| диапазоны | из 30 параметров с числовыми границами, например «40…45 HRC», — у скольких обе границы верны | больше |
| Ячейки: верно | из 112 ячеек — сколько совпали с эталоном полностью | больше |
| CER | доля ошибочных символов в ячейке: число правок, делённое на длину большей из двух строк, среднее по ячейкам. 0,05 — 5 ошибок на 100 символов | меньше |
| с на лист / блок / ячейку | время ответа на этом Mac (Apple M5, 32 ГБ), без загрузки модели | меньше |

## Почему так — предположения

- **Целый лист — это задача на понимание макета.** Реальные листы — бланки до ЕСКД: поля стоят в разных местах, часть написана от руки. Маленькие и OCR-модели читают буквы, но не понимают, какое поле где. Qianfan-OCR в режиме Markdown выдаёт текст только части листа, обычно таблицу или ТТ, и до основной надписи часто не доходит.
- **Qwen3.8-27B на листах хуже, чем Qwen3.6-27B (28 полей против 40), а на вырезках они равны.** Она проиграла почти по всем полям сразу, а не по одному. Предположение: сборка MLX иначе сжимает большое изображение, и мелкий текст теряется. Это не проверено.
- **На вырезках все модели намного лучше Tesseract.** В ТТ много знаков (±, Ø, HRC, «…»), шрифт неровный, на сканах шум. Модель знает, как обычно пишутся ТТ, и достраивает знаки по смыслу.
- **У Qianfan-OCR в режиме Markdown ячеек верно меньше (71 против 90), а CER ниже.** Без инструкции на русском она пишет кириллицу похожими латинскими и греческими буквами. Латиницу нормализация исправляет, греческую «Δ» вместо «Д» — нет. Текст почти верен, но целиком не совпадает.
- **PaddleOCR-VL на целом листе не измерена.** LM Studio падает на её токенах координат — это проблема сервера, а не модели. На кусках листа она зацикливается. Почему у неё мало верных диапазонов в ТТ (12 из 30), пока не разбирали.
- **Gemma 4 E4B выдумывает чаще всех** (10 полей из 52): маленькая модель заполняет схему хоть чем-нибудь.
- **ТТ и ячейки на синтетике — верхняя граница.** Вырезка сделана по разметке, поэтому поиск области не измерен. Синтетические сканы чище реальных.
- **100 % по ТТ недостижимы ни для кого.** Часть формулировок не знает парсер ядра: это пробелы этапа 5.

## Что дальше

1. Прогнать остальные скачанные модели: очередь берёт их сама по мере загрузки. Ближайшая — Gemma 4 31B, около 00:30.
2. Запустить три OCR-модели MLX, каждую с промптом из её карточки. Если LM Studio их не возьмёт, понадобится отдельный сервер, например mlx-vlm.
3. Проверить предположение о разрешении для Qwen3.8-27B: подать тот же лист кусками или крупнее.
4. По замерам распределить роли:
   - модель целого листа — найти и прочитать поля;
   - модель вырезок — ТТ и ячейки;
   - быстрая OCR-модель — сплошной текст.
5. Записать решение новым ADR поверх ADR-0014: модель становится основным путём чтения растров и сканов, а не дочитывает за OCR.
