# Правила кода и порядок работы

Версия от 13.11.2026. Дополняет [CONTRIBUTING.md](../CONTRIBUTING.md): там — что должно быть в проекте, здесь — как писать и менять код, чтобы его принял человек, который его не писал. Основание — [обзор 13.11.2026](reviews/2026-11-13-review.md).

Мера одна: новый человек понимает функцию за минуту, не открывая ADR, и может изменить её, не боясь сломать соседнюю.

## 1. Что уже хорошо и ломать нельзя

- Контракт отчёта в `kdcheck.schemas`, версия, JSON Schema и типы веба из неё.
- Настройки в `configs/*.yaml` с проверкой моделями; в коде ядра нет порогов.
- Границы модулей под import-linter: API берёт из ядра четыре модуля, блоки 1 и 2 друг друга не импортируют.
- У каждого значения есть источник; плохой файл, лист или стадия не останавливают прогон.
- На каждое правило — тест на срабатывание и на близкий случай, где оно молчит.
- ruff без замечаний; в ядре нет ни одного `noqa` и `type: ignore`.

Чистка не трогает ничего из этого списка.

## 2. Правила

### 2.1. Функция делает одно дело

- Ориентир — до 40 строк и сложность до 12. Длиннее — значит, внутри несколько шагов; у каждого шага своё имя.
- Одно правило Блока 1 — одна функция с идентификатором правила в имени или в первой строке описания. Сейчас `_check_duplicates` содержит пять правил: `B1.DUP.001`–`004` и `B1.VERSION.001`.
- Функция возвращает результат, а не дописывает его в списки, которые ей передали.

Было, `pipeline.py`:

```python
def _classify_and_parse(self, doc, specs: list[...], parts: list[PartRecord]) -> None:
    ...
    specs.append((doc, spec))
    ...
    parts.append(self._parse_drawing(doc, page, geom))
```

Стало:

```python
@dataclass
class ParsedDocument:
    specification: Specification | None = None
    part: PartRecord | None = None


def _parse_document(self, doc: LoadedDocument) -> ParsedDocument: ...
```

Вызывающий код сам раскладывает результат по спискам, и в тесте виден вход и выход.

### 2.2. Состояние прогона — явное

`BaselinePipeline` хранит данные одного прогона в полях объекта и обнуляет их в начале `run`: `vlm_problem`, `vlm_used`, `later_sheets`, `named_unread`, `eskd`. Метод `_set_sheet` по дороге дописывает в `later_sheets`. Читатель не видит, откуда берётся значение, а сброс легко забыть. Уже забыт: счётчики вызовов модели `calls` между прогонами не обнуляются, а `engines()` решает по ним, называть ли модель в отчёте. Скрипты `eval/` обрабатывают одним объектом много комплектов, и отчёт следующего комплекта может назвать модель, которую он не вызывал.

- Данные прогона живут в объекте прогона, который создаётся в `run` и передаётся дальше, либо возвращаются из функций.
- Функция, которая что-то меняет в аргументе, говорит об этом именем: `mark_…`, `add_…`, `set_…`. Функция с именем-существительным или `find_…`, `parse_…` ничего не меняет.
- Одинаковые блоки не копируются: обращение к модели с перехватом `VlmError` сейчас написано трижды — в `_read_cells`, `_read_requirements`, `_read_spec_cells` — и в одном из трёх ведёт себя иначе.

### 2.3. Имена

Полные слова из глоссария. Сокращение допустимо в цикле на три строки и в формуле.

| Сейчас | Писать |
| --- | --- |
| `des` | `designation` |
| `tb` | `title_block` |
| `ln`, `pg` | `line`, `page` |
| `geom` | `geometry` |
| `ex` | `extracted` |
| `eskd` | `designations`; в конвейере — `all_designations` и `kit_designations` |
| `fit, rough, hard, chem, geo, rare` | `rules.tight_fit` и так далее по месту |
| `loose`, `kept`, `named`, `later`, `head` | то, что в переменной лежит: `unassembled`, `kept_spec_ids`, `unread_named_files` |

- Один предмет — одно имя во всём коде. Сейчас глоссарий называет комплект `doc_set`, а код — `kit`; расхождение — `finding`, а код — `discrepancy`; источник текста в пояснениях назван `reader`, и в глоссарии этого слова нет. Глоссарий приводится к коду, новые слова сначала попадают в глоссарий.
- Логические значения — `is_…`, `has_…`. Множества и словари — во множественном числе с тем, что в них лежит: `designations_by_file`.
- Переименование делается средствами редактора по всему проекту, отдельным коммитом без других правок.

### 2.4. Пояснения в коде

Описание отвечает на три вопроса: что функция получает, что возвращает или меняет, какой пример это показывает. Причина решения — одной фразой и ссылкой на ADR.

- Простые предложения до 20 слов, подлежащее и сказуемое в начале. Без цепочек «of … of … whose».
- Первая строка — повелительное наклонение или существительное, по ней функцию находят в списке.
- Пример входа и выхода обязателен у разбора текста: регулярное выражение без примера не читается.
- В коде нет истории: «раньше», «теперь», «исправлено» — это текст коммита.
- Комментарий не пересказывает строку под ним. Если без комментария строка непонятна, сначала попробовать имя.

Было:

```python
def _named_unread(self, doc: LoadedDocument) -> None:
    """A file whose content is not read — damaged, encrypted, an unreadable scan — whose name gives a designation:
    the document of that designation is in the kit, not read. It closes its position, and it is no unknown
    document that may be the one another position misses."""
```

Стало:

```python
def _mark_unread_file_by_name(self, doc: LoadedDocument) -> None:
    """Take the designation of an unreadable file from its file name.

    Applies to damaged, encrypted and unreadable files. The file then counts as the document
    with that designation, but an unusable one: the finding for its position stays and names
    the file. Findings for other positions do not list it among unknown documents (ADR-0029).

    Example: a damaged "АРМ.303411.101 Корпус.pdf" is named in the finding for АРМ.303411.101.
    """
```

Старый текст к тому же устарел: «It closes its position» описывает поведение до коммита `20b08b5`, после него находка остаётся и называет файл. Описание, которое трудно прочитать, трудно и заметить неверным.

У 93 публичных функций ядра из 224 описания нет. Сначала описываются `run.py`, `pipeline.py`, `checks/`, `tree/`, `params/`: с них начинают читать.

### 2.5. Сообщения отчёта

Текст для технолога собирается из именованных частей, без вложенных условий внутри строки.

Было, `checks/completeness.py`:

```python
f"Сборочная единица {node.designation} указана в спецификации, но её спецификация в комплекте "
+ (f"не прочитана: {_named_files(files)}" if files else "отсутствует")
+ ("; сборочный чертёж есть, состав раскрыть невозможно" if node.drawing_document_ids
   else "; сборочного чертежа также нет")
+ tail,
```

Стало:

```python
spec_state = f"не прочитана: {_named_files(files)}" if files else "отсутствует"
drawing_state = (
    "сборочный чертёж есть, состав раскрыть невозможно"
    if node.drawing_document_ids
    else "сборочного чертежа также нет"
)
message = (
    f"Сборочная единица {node.designation} указана в спецификации, "
    f"но её спецификация в комплекте {spec_state}; {drawing_state}{tail}"
)
```

### 2.6. Ошибки

- `except Exception` — только на границах изоляции: файл, лист или кадр, стадия, задание. Сейчас так и есть, новых мест не добавлять. В остальном коде перехватывается конкретное исключение.
- Ошибку настроек или окружения видит пользователь: она попадает в журнал отчёта, а не только в журнал процесса. Пример: не найден настроенный распознаватель ячеек.
- `assert` не проверяет входные данные.

### 2.7. Повторы

- Перед новой вспомогательной функцией — поиск по проекту. Сейчас `_union` есть в трёх модулях ядра, `_crop`, `_same`, `_walk` — в двух, в `eval/` — восемь функций `markdown`, по два `_ratio` и `_centre`.
- Общее для ядра — в один модуль геометрии и текста. Общее для замеров — в `eval/common.py`: таблица Markdown, доля с проверкой нуля, строка окружения.
- Обобщение появляется со вторым случаем, не раньше. Параметр, ветка и класс без вызова и теста удаляются.

### 2.8. Тесты

- Имя — проверяемое поведение, коротко: `test_roughness_restores_lost_decimal_comma` вместо `test_a_roughness_ocr_read_without_its_decimal_sign_gets_the_preferred_value`.
- Один тест — одно поведение. Таблица случаев через `parametrize` с подписью к каждому, как сейчас.
- Тест проверяет результат, а не повторяет реализацию: если заменить формулу в коде на неверную, тест должен упасть.
- Отчёт целиком сравнивается с сохранённым на трёх контрольных наборах: демо-комплект, корпус сида 1, `arm-1` с кэшем прочтений. Различие либо объяснено в PR, либо правка откатывается.

### 2.9. Скрипты замеров

- Скрипт вызывает публичные функции ядра. `eval/drawing_field.py` сейчас наследует `BaselinePipeline` и переопределяет закрытый метод `_annotations`: для опыта допустимо, для выбранного пути — нет. Выбранный способ чтения переезжает в ядро настройкой, скрипт только включает её.
- Константы опыта — в начале файла с единицей и причиной, как сейчас.
- Графа, которая не считается, из таблицы убирается: пустая графа читается как ошибка замера.

### 2.10. Коммиты и PR

Сообщение говорит, что изменилось и на каком примере, обычным порядком слов.

| Было | Стало |
| --- | --- |
| `fix(core): a point a reader puts before the document code keeps the code` | `fix(core): read the document code after a stray dot from OCR ("…001. СБ")` |
| `fix(core): the finding of a position names its file not read instead of closing it` | `fix(core): keep the missing-document finding and name the unreadable file in it` |

- Один PR — одна тема, ориентир до 400 строк без сгенерированных файлов.
- Переименование, перенос кода и изменение поведения — три разных коммита.
- В описании PR: что проверено и чем отличаются контрольные отчёты.

### 2.11. Документы

- План — это шаги и отметки. Числа и ход работы — в отчётах, ADR и результатах замеров, план на них ссылается.
- Одно число записано в одном месте. Остальные документы ссылаются на `docs/EVALUATION.md`.
- Пункт списка — до 400 знаков. Длиннее — это раздел или отдельный документ.
- ADR пишется, когда были варианты и выбор что-то стоит. Исправление ошибки — коммит и тест, не ADR.

## 3. Порядок работы над изменением

1. Найти шаг в [PLAN.md](PLAN.md). Записать одной фразой, что изменится для пользователя отчёта.
2. Прочитать код, который меняется, и его тесты. Найти, нет ли уже нужной функции.
3. Написать тест, который сейчас падает: срабатывание и близкий случай.
4. Сделать правку наименьшего размера. Не трогать соседний код «заодно».
5. Запустить проверки из CONTRIBUTING и сравнение контрольных отчётов.
6. Прочитать свой diff целиком по списку раздела 5.
7. Обновить документ, если изменились контракт, настройки или план. Открыть PR.

Чистка кода идёт тем же порядком, но шаг 3 заменяет сравнение отчётов: поведение-сохраняющая правка не меняет ни одного отчёта.

## 4. Как ставить задачу

Задача, поставленная одной фразой, возвращается большим PR с лишним кодом. В постановке пять частей:

1. Цель: что должно стать верным, на каком входе.
2. Границы: какие файлы можно менять и какие нельзя; контракт, настройки и тесты других модулей — нельзя без отдельного решения.
3. Приёмка: какой тест должен пройти, какие отчёты не должны измениться.
4. Размер: ориентир в строках; если выходит больше — остановиться и показать план.
5. Порядок: сначала план из трёх-пяти шагов и список затрагиваемых функций, код — после согласия с планом.

Результат принимается по разделу 5, а не по тому, что тесты прошли.

## 5. Проверка перед PR

- [ ] Каждую строку diff я могу объяснить.
- [ ] Нет кода «на всякий случай»: параметров, веток, классов без вызова и теста.
- [ ] Нет новой функции рядом с почти такой же.
- [ ] Функции до 40 строк; длиннее — есть причина в описании PR.
- [ ] Имена — полные слова из глоссария; новых слов нет либо они добавлены в глоссарий.
- [ ] У публичной функции есть описание: вход, выход, пример.
- [ ] Комментарии не пересказывают код и не рассказывают историю.
- [ ] Перехват исключений — конкретный, кроме границ изоляции.
- [ ] Порог или словарь — в `configs/`, с единицей в комментарии.
- [ ] Тест падает без правки и проверяет результат, а не реализацию.
- [ ] Контрольные отчёты совпали либо различие объяснено.
- [ ] Удалено не меньше, чем можно было удалить: старый путь, который заменён новым, не оставлен.
- [ ] Документы с числами не разошлись с результатами замеров.

```toml
[tool.ruff.lint.mccabe]

[tool.ruff.lint.pylint]
max-statements = 60
max-branches = 15
max-args = 7
```

С этими порогами сейчас 48 замечаний: 14 по сложности — 12 функций и два теста, 16 по числу аргументов, веток и строк, 18 по именам и упрощениям. Порядок введения: включить правила, перечислить нарушителей в `per-file-ignores` со ссылкой на список раздела 7, убирать из списка по мере чистки. Новых исключений не добавлять.

Дополнительно:

- сравнение контрольных отчётов — отдельной командой и в CI для демо-комплекта;
- покрытие ядра тестами с порогом на уровне текущего значения, чтобы оно не падало;
- для веба — линтер и форматтер в `npm run lint` и в CI;
- раз перед передачей — поиск неиспользуемого кода (`vulture`) и удаление найденного.

## 8. Признаки кода, который придётся переписывать

По ним проверяется чужой и свой PR.

- Обработка ошибок, которые не могут случиться, вместо одной проверки на границе.
- Параметр или настройка, которыми никто не пользуется.
- Две функции, отличающиеся одной строкой.
- Обёртка, которая только передаёт вызов дальше.
- Описание длиннее функции, и без ADR его не понять.
- Имя, придуманное на месте, которого нет в глоссарии.
- Тест, который проходит при любой реализации.
- PR на тысячу строк, где исправление смешано с переносом кода.
- Документ, который растёт с каждой задачей и ни разу не сократился.

## 9. Пример рецепта для передачи: новое правило Блока 1

Такие рецепты — содержание `docs/HANDOVER.md`: правило Блока 1, грамматика обозначений, форма основной надписи, шаблон параметра технических требований.

1. `kdcheck/checks/rules.py`: строка в `RULES` — идентификатор вида `B1.NAME.001`, тип расхождения, заголовок.
2. `configs/checks.yaml`: правило включено, важность задана. Без записи прогон остановится с именем правила.
3. `kdcheck/checks/completeness.py`: функция правила и её вызов в `Checker.run`.
4. `packages/kdcheck/tests/test_completeness.py`: случай срабатывания и близкий случай в `CASES`.
5. `docs/report-format.md`: строка каталога правил; тест сверяет каталог с реестром.
6. `synth/src/synth/mutations.py`: мутация с ожидаемым расхождением, чтобы полнота правила мерилась.
7. Новый тип расхождения — это изменение контракта: `kdcheck/schemas`, версия, `scripts/export_schema.sh`, подпись типа в `frontend/src/lib/labels.ts`.
