# Техническая документация проекта

Автоматизированная проверка комплектности конструкторской документации для производства самоходной техники.

## Что это за проект

Технологи на производстве АРМ вручную проверяют комплекты чертежей и спецификаций перед запуском в производство — на это уходит от нескольких часов до нескольких дней на изделие. Часть расхождений обнаруживается уже при изготовлении: отсутствующий чертёж останавливает участок, непрочитанное требование к точности оборачивается браком.

Мы делаем сервис, который проверяет комплект автоматически и выдаёт отчёт с расхождениями и критичными параметрами. Технолог получает список проблем с прямыми ссылками на исходные документы вместо многочасовой ручной сверки.

**Вход:** папка с PDF и JPG файлами — чертежи, сборочные чертежи, спецификации  
**Выход:** веб-отчёт с деревом изделия, расхождениями и таблицей параметров деталей

## Что уже работает

### Веб-интерфейс и API

Загружаешь папку с комплектом — получаешь отчёт. Работает на http://127.0.0.1:8000 после запуска `python -m arm_web serve` из `backend/`.

- Загрузка комплекта целиком (drag-and-drop папки)
- Отслеживание прогресса обработки
- Просмотр отчёта по вкладкам: дерево изделия, расхождения, параметры деталей, критичные параметры
- Клик по значению открывает исходный документ с подсветкой области, из которой оно взято
- Выгрузка результатов в Excel и HTML

Демо-отчёт открывается сразу на главной странице без загрузки своих файлов.

### Ядро проверки (kdcheck)

Пакет `packages/kdcheck` — самостоятельная библиотека, которая делает всю работу. API только вызывает её.

**Что распознаётся:**
- Векторные PDF читаются напрямую из текстового слоя (быстро и точно)
- Сканы распознаются через Tesseract OCR
- Основная надпись чертежа: обозначение, наименование, материал, масса, масштаб, литера
- Спецификации: позиция, обозначение, наименование, количество
- Технические требования: квалитеты, шероховатость Ra/Rz, термообработка, покрытия

**Блок 1 — проверка комплектности:**
- Строит дерево изделия по спецификациям (сборочные единицы раскрываются рекурсивно)
- Сверяет позиции в спецификациях с фактическими файлами чертежей
- Находит 12 типов расхождений: нет чертежа, чертёж без спецификации, расхождение наименования, дубль обозначения, несовпадение литеры/номера изменения

**Блок 2 — анализ документов:**
- Извлекает параметры деталей в единую таблицу
- Выделяет критичные параметры (Ra ≤ 0,8, квалитет IT6 и точнее) с обоснованием

**Изоляция ошибок:**
Повреждённый файл, посторонний документ или нечитаемый скан не прерывают обработку комплекта — они попадают в отчёт отдельной категорией.

### Качество на данный момент

Замерено на демо-комплекте (синтетический, 22 файла):
- **Расхождения:** точность и полнота 100%
- **Основные надписи векторных PDF:** 100%
- **Основные надписи сканов:** 63% (OCR не всегда находит материал, не читает вертикальные графы)
- **Параметры технических требований:** точность 99%, полнота 94%

На 20 синтетических комплектах с заложенными ошибками (78 расхождений):
- Найдено 71 из 78, точность 57%, полнота 91%
- Основная проблема: деталь «БЧ» (без чертежа) в графе «Формат» даёт 39 ложных срабатываний — ядро ищет эту пометку только в примечании

Синтетика проще реальных комплектов, это проверка работоспособности. Для оценки на документах АРМ нужна эталонная выборка из реальных комплектов.

## Технологии и почему они

### Backend
**Python 3.11+, FastAPI** — стандарт для ML-сервисов, удобная асинхронность и автодокументация API

**pypdfium2 (Apache/BSD)** — чтение текстового слоя и растеризация PDF. Альтернатива PyMuPDF отвергнута из-за лицензии AGPL. Результаты идентичны PyMuPDF на всех полях демо-комплекта, работает в 10 раз быстрее на рендере.

**Tesseract OCR** — опенсорсный движок распознавания, русский + английский. Ставится отдельно (`apt install tesseract-ocr tesseract-ocr-rus`).

**uv** — менеджер зависимостей Python, быстрее pip, поддерживает workspace с несколькими пакетами.

### Frontend
**React 18 + TypeScript, Vite** — современный стек для веб-приложений, быстрая сборка

**TanStack Query** — управление состоянием и кэширование запросов к API

**Recharts** — графики распределений параметров

### Архитектура

```
frontend/          Веб-интерфейс (React)
  └─ API запросы к backend

backend/           FastAPI сервис
  └─ вызывает kdcheck.run()

packages/kdcheck/  Ядро проверки (независимая библиотека)
  ├─ ingest/       Чтение файлов, текстовый слой, OCR
  ├─ extract/      Основная надпись, спецификации, техтребования
  ├─ tree/         Дерево изделия
  ├─ checks/       Правила проверки комплектности (Блок 1)
  ├─ params/       Параметры деталей и критичность (Блок 2)
  └─ report/       Выгрузки Excel, HTML

synth/             Генератор синтетических данных
  ├─ model.py      Модели документов
  ├─ render.py     Рисование листов (reportlab)
  ├─ kits.py       Случайные комплекты с мутациями
  └─ truth.py      Эталонная разметка
```

**Почему правила, а не нейросети**
Векторные PDF из САПР уже содержат текст с координатами. Геометрия форм задана ГОСТ 2.104/2.106, поэтому простые правила по координатам дают точные значения без обучения моделей. Для сканов используем OCR, затем те же правила.

**Настройки отделены от кода**
Пороги, шаблоны форм ГОСТ, словари — в `configs/*.yaml`. Калибровка без пересборки, каждый отчёт хранит хэш настроек.

### Контракт данных

`packages/kdcheck/src/kdcheck/schemas/` — формат отчёта в виде Pydantic моделей. Это контракт между ядром и веб-интерфейсом. Отчёт любого конвейера, соответствующий схеме, откроется в веб-интерфейсе.

JSON Schema и TypeScript типы генерируются из этих моделей автоматически (`scripts/export_schema.sh`), CI сверяет их при каждом коммите.

## Как запустить локально

### Требования
- Python ≥ 3.11
- Node.js ≥ 20
- Tesseract с русским языком: `brew install tesseract tesseract-lang` (macOS) или `apt install tesseract-ocr tesseract-ocr-rus` (Linux)

### Быстрый старт

```bash
# 1. Backend
python -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt
pip install --no-deps ./packages/kdcheck

# 2. Frontend
cd frontend && npm ci && npm run build && cd ..

# 3. Запуск
cd backend && python -m arm_web serve
# Откроется http://127.0.0.1:8000
```

На главной странице есть кнопка «Демо-отчёт» — можно сразу посмотреть, как выглядит результат.

Для загрузки своего комплекта: «Новая проверка» → выбираешь папку → ждёшь обработки → смотришь отчёт.

### Режим разработки

Backend с горячей перезагрузкой:
```bash
cd backend
python -m arm_web serve --reload
```

Frontend с горячей перезагрузкой:
```bash
cd frontend
npm run dev
# Откроется http://localhost:5173
# Запросы /api проксируются на :8000
```

### Командная строка

Можно обрабатывать комплекты без веб-интерфейса:

```bash
uv run kdcheck run samples/demo_kit -o out
# Создаст out/report.json, report.xlsx, report.html
```

## Как работают правила проверки (Блок 1)

Правила проверки комплектности — это не нейросети, а логические правила на основе извлечённых данных. Каждое правило описано в коде, покрыто тестами и управляется через конфиг.

**Где что лежит:**
- `packages/kdcheck/src/kdcheck/checks/rules.py` — каталог всех правил: идентификатор (например `B1.MISSING.001`), тип расхождения, заголовок
- `packages/kdcheck/src/kdcheck/checks/completeness.py` — логика проверок
- `configs/checks.yaml` — какие правила включены и с какой важностью (high/medium/low)

**Примеры правил:**

**B1.MISSING.001** — чертёж детали отсутствует
Логика: позиция есть в разделе спецификации «Детали», но документа с таким обозначением нет в комплекте (кроме позиций «БЧ» — без чертежа)

**B1.ORPHAN.001** — чертёж не входит ни в одну спецификацию
Логика: документ есть в папке, но его обозначение не встречается ни в одной спецификации и не является корнем дерева изделия

**B1.NAME.001** — наименование на чертеже не совпадает со спецификацией
Логика: обозначение одно, но наименование в основной надписи чертежа отличается от наименования в спецификации (с нормализацией пробелов и нечётким сравнением, чтобы опечатки OCR не давали ложных срабатываний)

**B1.DUP.001** — обозначение встречается в нескольких документах
Логика: два или более файлов с разным содержимым имеют одно обозначение в основной надписи (побайтовые копии исключены — они получают статус `duplicate_file`)

**Как добавить новое правило:**
1. Добавь запись в `RULES` в `rules.py`
2. Добавь логику проверки в `completeness.py`
3. Добавь настройки в `configs/checks.yaml`
4. Напиши тест, где правило срабатывает, и тест, где оно молчит (близкий случай)

## LLM и VLM модели: где и как используются

**Текущее состояние:** LLM и VLM в коде пока не используются. Вся обработка идёт через текстовый слой PDF, OCR и правила.

**Где планируется использовать:**

### Технические требования (частично уже работает)
Сейчас: регулярные выражения + словари из `configs/dictionaries.yaml`
Планируется: LLM для «длинного хвоста» формулировок технических требований, которые не покрываются правилами

**Кандидаты:**
- Qwen3.5 (Apache 2.0) — structured output по JSON-схеме
- GigaChat 3 (MIT, открытые веса) — русский язык
- Yandex GPT (коммерческий, только с разрешения АРМ)

**Как тестировать:**
1. Создай эталонную выборку пунктов техтребований с разметкой (что извлекать)
2. Запусти модель с промптом и JSON-схемой
3. Сравни результат с эталоном (точность, полнота, F1)
4. Файл с метриками в `eval/results/`, промпты в репозиторий

### Основная надпись на нестандартных бланках
Сейчас: шаблоны ГОСТ 2.104 по координатам
Планируется: VLM для чтения нестандартных штампов и рукописных правок

**Кандидаты:**
- PaddleOCR-VL 0.9B/1.6B (Apache 2.0) — документный OCR, 109 языков включая русский, №1 в обзоре Roboflow (96.34% на OmniDocBench)
- Qwen3-VL от 0.8B (Apache 2.0) — общего назначения, можно дообучить на LoRA
- Yandex Vision OCR (коммерческий) — модели `table`, `handwritten` для русского

### Размеры и допуски на поле чертежа
Сейчас: не извлекается (MVP — только техтребования над основной надписью)
Планируется: детектор + VLM для размеров с допусками, рамок допусков формы

**Кандидаты:**
- eDOCr2 (MIT) — специально для чертежей
- YOLO11 (AGPL — только по решению) + Donut или Florence-2 (MIT)
- Qwen3-VL с дообучением (по примеру Khan et al., 2024 — Florence-2 на 400 чертежах обошла GPT-4o)

**Как попробовать модель:**

```bash
# 1. Подготовь эталонную выборку: вырезки из чертежей + ожидаемый результат
# Формат: data/eval_samples/<задача>/images/ и truth.json

# 2. Напиши скрипт вызова модели в eval/<задача>.py
# Пример структуры:
#   - загрузка эталона
#   - вызов модели по каждому примеру
#   - расчёт метрик (точность, полнота, F1, CER)
#   - сохранение результатов в eval/results/<задача>.json и .md

# 3. Запусти замер
uv run python eval/<задача>.py

# 4. Опиши результаты в eval/results/<задача>.md
# Что измерялось, какие модели, на каких данных, какие метрики получены
```

**Пример из проекта:** `eval/pdf_backends.py` — сравнение pypdfium2 и PyMuPDF на демо-комплекте, результаты в `eval/results/pdf-backends.md`

**Учебные материалы:**
- Сайты кафедр инженерной графики (поиск: `"чертежи деталей" ЕСКД filetype:pdf`)
- Университеты: МГТУ Баумана, СПбПУ, МАИ
- Методички по черчению и конструированию

**GitHub и форумы:**
- GitHub: поиск `GOST drawing`, `ЕСКД чертеж`, `KOMPAS`

### Типичные проблемы и решения

```python
from transformers import AutoModel, AutoProcessor
import torch
from PIL import Image

# Загрузка модели (пример с PaddleOCR-VL)
model_name = "PaddlePaddle/PaddleOCR-VL"
model = AutoModel.from_pretrained(model_name, trust_remote_code=True)
processor = AutoProcessor.from_pretrained(model_name, trust_remote_code=True)

# Промпт для извлечения полей основной надписи
prompt = """Extract the following fields from the engineering drawing title block:
- Designation (Обозначение)
- Name (Наименование)
- Material (Материал)
- Mass (Масса)
- Scale (Масштаб)

Return as JSON with keys: designation, name, material, mass, scale.
If field is empty or unclear, use null."""

# Обработка изображения
image = Image.open("sample_drawing.pdf")  # или из PDF страницы
inputs = processor(images=image, text=prompt, return_tensors="pt")

# Inference
with torch.no_grad():
    outputs = model.generate(**inputs, max_new_tokens=256)
    result = processor.decode(outputs[0], skip_special_tokens=True)

print(result)  # {"designation": "...", "name": "...", ...}
```

### Метрики качества для VLM

```python
# eval/metrics.py

def calculate_field_accuracy(predictions, ground_truth):
    """Точность извлечения по полям"""
    correct = 0
    total = len(ground_truth)
    
    for pred, true in zip(predictions, ground_truth):
        if pred["designation"] == true["designation"]:
            correct += 1
    
    return correct / total if total > 0 else 0

def calculate_cer(predictions, ground_truth):
    """Character Error Rate для OCR"""
    import Levenshtein
    
    total_distance = 0
    total_length = 0
    
    for pred, true in zip(predictions, ground_truth):
        pred_text = pred.get("name", "")
        true_text = true.get("name", "")
        
        total_distance += Levenshtein.distance(pred_text, true_text)
        total_length += len(true_text)
    
    return total_distance / total_length if total_length > 0 else 0

def calculate_f1(predictions, ground_truth, field):
    """F1 для конкретного поля"""
    tp = sum(1 for p, t in zip(predictions, ground_truth) 
             if p.get(field) and p[field] == t[field])
    fp = sum(1 for p, t in zip(predictions, ground_truth) 
             if p.get(field) and p[field] != t.get(field))
    fn = sum(1 for p, t in zip(predictions, ground_truth) 
             if not p.get(field) and t.get(field))
    
    precision = tp / (tp + fp) if (tp + fp) > 0 else 0
    recall = tp / (tp + fn) if (tp + fn) > 0 else 0
    
    return 2 * precision * recall / (precision + recall) if (precision + recall) > 0 else 0
```
