# Эталон на реальных документах

Два набора из корпуса открытых чертежей ([open_drawings.csv](../open_drawings.csv)) и комплекты АРМ ([ниже](#комплекты-арм)). Из корпуса — учебные комплекты для Блока 1 — что лежит в каждом файле и какие расхождения должна найти проверка, и отдельные листы производственной КД — что записано в основной надписи. Формат — `KitTruth` из [synth/truth.py](../../synth/src/synth/truth.py), как у синтетических комплектов: отчёт с обоими сравнивает один и тот же код.

## Комплекты АРМ

Данные заказчика: файлы, разметка и всё, что раскрывает их содержание, лежат в `data/arm` вне git. Реестр `data/arm/kits.json` связывает обезличенный идентификатор с папкой комплекта и его ролью, манифест `data/arm/manifest.json` хранит sha256 каждого файла; `eval/arm_kits.py verify` сверяет файлы с ним. В репозиторий попадают только числа ([arm-kits.md](../results/arm-kits.md)).

| Комплект | Роль | Что размечаем |
| --- | --- | --- |
| `arm-1` | dev: на нём настраиваются правила | целиком, в `KitTruth`: каждый документ, каждая строка спецификации, расхождения; две разметки, `a` и `b` |
| `arm-2`, `arm-3` | test: меряются один раз, на замороженных правилах | для Блока 2 — стратифицированная выборка листов: вектор и растр × спецификация, сборочный чертёж, деталь × формат; 15–20 % листов — дважды. Для Блока 1 — файловые мутации (пункт 4.8 плана) и разбор каждого срабатывания |
| `arm-4` | вне разбиения | пока ничего: что это за листы, уточняем у АРМ |

Разбиение — по комплектам: листы одного комплекта оформлены одинаково, и разбиение по листам перенесло бы оформление test в dev. Правила по-прежнему проверяются и на синтетике, и на открытых комплектах.

Разметка комплекта АРМ — `data/arm/gold/<комплект>.<метка>.json`, согласованная — `data/arm/gold/<комплект>.json`; делается по маскированным копиям листов из `data/arm/masked`. Документы в ней названы именами файлов комплекта, как их хранит файловая система и манифест, последующие листы документа — в `sheet_files`. Размечают на локальной странице `uv run python eval/gold_label.py arm-1 --by a`: она показывает маскированные листы рядом с формой документа, рамки пунктов ТТ и параметров обводятся мышью, а каждое сохранение пишет `data/arm/gold/<комплект>.<метка>.json`, сохраняет предыдущую версию в `.bak` и проверяет файл, как `eval/gold.py check`. Новая разметка начинается только с имён файлов: файлы «…(N)» одного имени — листы одного документа, «СП» и «СБ» в имени — вид. Другие разметки и отчёты ядра страница не читает. Сервер слушает только 127.0.0.1, листы с машины не уходят. `eval/gold.py check` проверяет эти файлы там, где есть `data/arm`: каждое имя — из манифеста своего комплекта. `eval/gold.py agree` сравнивает и эти черновики: в [results/gold-agreement.md](../results/gold-agreement.md) попадают только числа согласия, по частям разметки, а список несовпадений и протокол спорных случаев лежат рядом с разметкой, в `data/arm/gold`: в них обозначения и наименования заказчика.

## Что размечено

| Где | Что |
| --- | --- |
| `root` | обозначение изделия верхнего уровня, без кода документа; `""`, если обозначения нет |
| спецификация | из основной надписи: `designation`, `name`, `litera`, `revision` — номер последнего изменения, `sheets`; строки — в `rows` |
| строка спецификации | `section` — раздел над строкой; `fmt`, `pos`, `designation`, `name`, `qty`, `note` — как в графах |
| чертёж | `designation`, `name`, `litera`, `revision`, `sheets`; также `material`, `mass`, `scale`, `archive_number`, `first_use` — по ним проверим основную надпись в Блоке 2 |
| групповой чертёж | таблица исполнений — `variants`: обозначение исполнения полностью и как записано, масса, графы таблицы в `data` |
| технические требования | `requirements` — пункты по порядку, `requirement_boxes` — область каждого пункта |
| параметр | `parameters`: `category` — категория отчёта, `name`, `value`, `value_min`, `value_max`, `unit`, `it_grade` — квалитет допуска, `box` — область надписи на листе; из ТТ и с поля чертежа |
| схема, перечень элементов, чертёж общего вида | вид `other`: `designation`, `name`, `litera`, `revision`, `sheets` |
| лист набора листов | основная надпись, как у чертежа; вид — из `sheets.csv` |
| `problem_files` | файл, который не документ комплекта: 3D-вид, титульный лист, технологический документ — статус `foreign` |
| `discrepancies` | расхождения, которые должна найти проверка: `type`, `designation`, `comment` — почему расхождение есть |
| `notes` | спорные случаи комплекта и решения по ним, по строке на случай |

Вид документа — по самому документу: чертёж общего вида модуля питания реестр относит к сборкам, в разметке он `other`. Технические требования и параметры размечены у комплекта `arm-1`; у открытых комплектов и набора листов — нет.

## Как записаны значения

- Как на листе: ошибки автора не исправлены, опечатка остаётся в значении — «песпаечных плат» на листах А1 модуля питания.
- С изображения листа, а не из текстового слоя PDF: у части файлов слой битый. У модуля питания кириллица в нём — байты UTF-8, прочитанные как UTF-16.
- Наименование в основной надписи — все строки графы через пробел, изделие и документ: «Паяное соединение Сборочный чертеж».
- Перенос строки внутри графы — один пробел, двойной пробел — один.
- Пустая графа — `""`; графы нет на бланке — `null`: у бланков ВЛ60 нет материала, масштаба и литеры, у «Наружных видов» УЭП-60-10 — ничего, кроме наименования и обозначения.
- Записанное не в своей графе — значение той графы, где оно стоит: в графе обозначения листов ИЖ-250 — наименование станка.
- Зачёркнутое — не значение: значение — действующая запись рядом с ним.
- Закрытое маской (`eval/mask_people.py`) и не читаемое — пусто, `""`. Видное наполовину, но читаемое однозначно — значение.
- Номер изменения — из графы «Изм.» последней записи изменений. Запись «Зам.» с пустой графой «Изм.» номера не даёт: `revision` — пусто, как на листе.
- Перенос слова с дефисом — слово целиком: «элек-тропитающее» — «электропитающее». Рукописные сокращения — как написаны: «Ток. винторезн.».
- Регистр, «ё», десятичная запятая, тире, кавычки и латинские буквы, похожие на русские, — как набраны: сравнение их не различает.
- Наименование на нескольких строках спецификации — одна строка `rows`, части через пробел.
- `section` — подчёркнутый заголовок над строкой: «Документация», «Сборочные единицы», «Детали», «Стандартные изделия», «Прочие изделия», «Материалы».
- Пункт технических требований — текст без номера, строки через пробел; пункт без номера — один пункт.
- Параметр из ТТ — по категориям отчёта, кроме `other`: общие допуски, твёрдость, термообработка, покрытие, шероховатость, допуск формы и расположения. Зазоры, моменты затяжки, углы и прочие требования без категории параметрами не размечаются.
- Параметр поля — размер с допуском, резьба с полем допуска, шероховатость с числом, рамка допуска формы и расположения, шероховатость остальных поверхностей в углу листа. Не параметр: справочный размер «*», сварной шов, фаска, знак шероховатости без числа.
- Имя параметра — как на листе и одной строкой: «Ø40H7», «Ø40+0,025», «50±0,1», «M20x1,5-6H», «Ra 1,6», «HRC», «IT14»; у рамки допуска формы и расположения — её знак, «⊥», «↗», «⌖», а число рамки — `value`. У размера `value` — номинал, `value_min` и `value_max` — предельные размеры, если отклонения записаны числами; у резьбы чисел нет.
- `it_grade` — у общих допусков из пункта ТТ (IT14); у размера с полем допуска — из поля; у размера с отклонениями числами — квалитет, значение IT которого по ГОСТ 25346 для интервала размера равно ширине допуска, иначе пусто. У других категорий квалитета нет.
- Область — страница и рамка надписи, доли листа от левого верхнего угла, как `SourceRef`; у параметра из ТТ — область его пункта. Область без значения — `null`: её не нашли на листе.

## Что считается верным извлечением

Правило одно для всех замеров `eval/`, и в коде оно записано один раз — [scoring.py](../scoring.py). По нему же сравниваются две разметки.

- **Текстовое значение** — поле основной надписи или графа строки спецификации — верно, если совпадает с разметкой после нормализации. Не различаются регистр, «ё» и «е», десятичная запятая и точка, пробелы и переносы строк, латинские буквы, похожие на русские (`latin_lookalikes` в `configs/dictionaries.yaml`), виды тире и кавычек, знак диаметра. Любое другое отличие — ошибка: неверная или лишняя буква, пропущенная цифра, потерянное слово.
- **Какие поля считаются.** Только непустые в разметке. Поле, которого ядро не прочитало, — ошибка, а не пропуск в подсчёте: доля верных — от всех непустых полей разметки.
- **Строка спецификации** найдена, если её обозначение после нормализации есть среди обозначений строк той же спецификации в отчёте.
- **Параметр** технических требований или поля чертежа найден, если в отчёте есть параметр той же категории, в имени, уточнении или исходном тексте которого есть имя параметра из разметки. Пары — один к одному, в порядке разметки; параметр отчёта без пары — лишний.
- **Значение параметра** верно, если у найденного параметра те же числа — значение, нижняя и верхняя граница, — та же единица и тот же квалитет, что задаёт разметка; чисел, которых разметка не задаёт, правило не проверяет. Доля верных значений даётся отдельно от полноты: параметр с неверным числом найден, но его значение неверно.
- **Область значения** — то, что отчёт показывает технологу как источник, — верна, если она на той же странице, что область из разметки, содержит её центр и не содержит центра ни одной другой области разметки того же документа: так область значения отличается от области всей основной надписи или листа. Значение из имени файла области на листе не имеет и не считается. Области знает синтетика — генератор записывает, где нарисовал каждое значение, — а у реальных комплектов разметка `arm-1`, у пунктов ТТ и параметров.
- **Расхождение Блока 1** найдено, если в отчёте есть расхождение того же правила — у синтетики — или того же типа — у реальных комплектов, где разметка называет типы, — с тем же обозначением. У реальных комплектов обозначения сравниваются после нормализации ядра, у синтетики генератор пишет их в том виде, в каком их пишет ядро.
- **Согласие двух разметок** считается по значениям, непустым хотя бы в одной из них, по тем же правилам: текст — после нормализации, область — по центру в обе стороны: каждая из двух областей содержит центр другой и не содержит центра ни одной другой области той же разметки в документе. Строки спецификаций, пункты технических требований и строки таблицы исполнений сопоставляются по порядку, и строка, которой нет в одной разметке, — одно несовпадение, а не сдвиг всех следующих. Параметры сопоставляются один к одному: сначала та же категория и то же имя в одной области, затем та же категория и то же имя по порядку, затем та же категория в одной области — имя, прочитанное по-разному. У пары сравниваются имя, числа, единица, квалитет и область.

## Какие расхождения размечены

Расхождение размечено, если технолог на входном контроле вернул бы его конструктору. Типы и правила — из [каталога](../../docs/report-format.md#правила-блока-1-discrepanciesrule_id). В `designation` — обозначение позиции или документа, к которому относится расхождение; если обозначения нет — `""` и наименование в `name`.

| Тип | Когда | Пример из этих комплектов |
| --- | --- | --- |
| `missing_drawing` | позиции из «Деталей» или документа из «Документации» нет в комплекте; позиции «БЧ» не в счёт | ИТМО: у деталей СУИР.06.06.04–08 нет чертежей; модуль питания: корпусные детали |
| `orphan_drawing` | документ комплекта не указан ни в одной спецификации | ИТМО: сборочный чертёж, «Документации» в спецификации нет; модуль питания: перечень элементов |
| `name_mismatch` | наименование на чертеже отличается от спецификации больше, чем регистром, «ё» и пунктуацией; у документов из «Документации» сравнивается наименование изделия | модуль питания: «…для песпаечных плат…» на листах А1, «…для беспаечных макетных плат…» в спецификации |
| `duplicate_designation` | одно обозначение у разных документов или у позиций с разными наименованиями | ЛЭТИ: ПМИГ 2208.23.001 — «Основание» и «Кожух»; ИТМО: спецификация обозначена СУИР.06.06.00.СБ, как сборочный чертёж |
| `revision_mismatch` | разные литеры или номера изменений у документов одного изделия | |
| `missing_specification` | у сборочной единицы нет своей спецификации | модуль питания: печатная плата |
| `position_anomaly` | у позиции нет обозначения или количества, номер позиции повторяется; в отчёте — с версии 1.8, правила `B1.POS.001`–`B1.POS.003`. Не аномалия: стандартные и прочие изделия и материалы без обозначения и пропущенные номера — ГОСТ 2.106 допускает их резервировать | модуль питания: позиции 1–3 без обозначений |

Остальные типы плана — `format_mismatch`, `sheets_missing`, `section_mismatch`, `first_use_mismatch` — в разметке допустимы; правила для них у ядра есть ([ADR-0027](../../docs/adr/0027-block1-rules.md)), а в этих комплектах таких расхождений нет.

## Двойная разметка

ИТМО и ЛЭТИ размечены дважды, независимо: 16 листов из 23, больше 15–20 %, которые требует план. Модуль питания размечен один раз. Согласие считается по значениям, которые есть хотя бы в одной разметке, после нормализации ([results/gold-agreement.md](../results/gold-agreement.md)): ИТМО — 1,00 (93 из 93), ЛЭТИ — 0,94 (147 из 156). Из девяти несовпадений ЛЭТИ восемь — значения, которых нет в одной из разметок: корень, основная надпись спецификации «Паяного соединения», расхождения; одно — прочтение, «Кажух» вместо «Кожух». Каждое несовпадение решено по листу.
